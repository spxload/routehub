## 1. ТАБЛИЦА ИЗМЕРЕНИЙ

### 1.1 Задержки и маршрутизация

| Что | Значение |
|---|---|
| `ctx.http` без политики → `cp.cloudflare.com/generate_204` | 204, 89–216 мс |
| то же с `policy` группы | 204, 91–224 мс |
| то же с `policy: DIRECT` | 204, 75–99 мс |
| то же с `policy` = имя узла ИЗ ПОДПИСКИ | **404**, `server: null` — отвечает сам Egern |
| то же с `policy` = несуществующее имя | **404**, `server: null` |
| то же с `policy: REJECT` | **404**, `server: null` |
| то же с `policyDescriptor` = имя узла | исключение `HTTP error! status: 400` |
| `HEAD`-запрос на тот же адрес | 204, **38 мс** |
| `redirect: 'manual'` на `http://www.cloudflare.com/` | **301** — редиректы не разворачиваются |
| недостижимый `192.0.2.1` при `timeout: 3000` | исключение через 61–503 мс, **таймаут не выдерживается** |
| пять параллельных запросов через группу | 109–211 мс на все пять (одиночный ~95 мс) |

**Почему `192.0.2.1`.** Это TEST-NET-1 из RFC 5737 — диапазон зарезервирован под
документацию и не маршрутизируется в интернете. Поэтому он недостижим и напрямую,
и через любой узел, что и делает его пригодным для проверки «применяется ли
групповой адрес пробы». Тот же приём годится для любой будущей проверки, где
нужен заведомо мёртвый адрес без риска задеть чужой сервер.

### 1.2 Хранилище

| Проба | Итог |
|---|---|
| `ctx.storage.set/get` строки | работает |
| `setJSON/getJSON` | работает |
| `delete` | работает, после него `get` даёт пусто |
| запись 32 768 байт | прочитано 32 768 |
| запись 262 144 байт | прочитано 262 144 |
| запись 1 048 576 байт | прочитано 1 048 576 |
| счётчик прогонов между запусками | сохраняется |
| перечисление ключей | **метода нет** |
| `$persistentStore.write` → `ctx.storage.get` | видно |
| `ctx.storage.set` → `$persistentStore.read` | видно |

Предел значения выше 1 МБ не нащупан — проба на большее не ставилась.

| Проба | Итог |

### 1.4 Сжатие и геолокация

| Проба | Итог |
|---|---|
| `ctx.compress.gzip` 576 байт | 36 байт |
| `ctx.compress.brotli` 576 байт | 26 байт |
| `gunzip` обратно | 576 байт, совпадение |
| `$utils.ungzip` нашего gzip (34 байта) | вернул объект длиной 288 |
| `$utils.geoip('8.8.8.8')` | `US`, ASN `15169`, `GOOGLE` |
| `ctx.lookupIP` для узлового IP | `PK`, `asn: null`, `organization: null` |
| `$utils.geoip` для того же IP | `PK`, `asn: null` |
| Cloudflare `trace` для него же | `loc=RU`, `colo=DME` (наблюдался и `ARN`) |

Вывод тот же, что в справочнике: **страна узла берётся только из имени**. Здесь
важна причина: база на устройстве не знает диапазонов провайдера, а не «ошибается
случайно» — для `8.8.8.8` те же функции отвечают полно и верно.

### 1.5 Сведения об устройстве (`ctx.device` и `$network`)

Оба источника дают одно и то же, в разной форме:
`wifi.ssid` = `fh_862d68_5G`, `wifi.bssid` = `c4:64:b6:86:2d:6c`,
`cellular.carrier` = `--` (на Wi-Fi), `cellular.radio` = `LTE`,
`ipv4.address` = `192.168.1.2`, `gateway` = `192.168.1.1`, `interface` = `en0`,
`ipv6.address` = пусто (при `ipv6: false` в профиле), `dnsServers` = `192.168.1.1`.

**В Loon доступен только `ssid`.** BSSID и тип радио — новое, и именно на них
опираются правила `conditional`.

## 2. ФОРМЫ ВЫЗОВОВ — ЧТО ИМЕННО ПРОБОВАЛИ

### 2.1 `ctx.http`
Методы: `get`, `post`, `put`, `patch`, `delete`, `head`, `options` — семь.
Параметры, проверенные на деле: `policy`, `timeout`, `headers`, `body`, `redirect`.
Заголовки ответа читаются (`r.headers.get('server')` → `cloudflare`).
Тело: `r.text()`, `r.arrayBuffer()` — оба работают.

### 2.2 `$httpClient` (прослойка Surge)

| Форма | Итог |
|---|---|
| `get(строка, cb)` | 204 — работает |
| `get({url}, cb)` | 200 — работает |
| `get({url, node}, cb)` | работает, но **`node` игнорируется** |
| `get({url, policy}, cb)` | работает, но **`policy` игнорируется** |
| `request({method, url}, cb)` | **роняет весь прогон** |

Игнорирование доказано по адресу выхода: все формы дали один и тот же IP,
совпадающий с выходом обычных правил, тогда как `ctx.http` с `DIRECT` давал
другой. Ошибка при падении выглядит как
`UNHANDLED PROMISE REJECTION: n is not a function … @ http://egern-js/`.

### 2.3 Что искали и не нашли
Перебраны сорок имён: `$httpAPI`, `$config`, `$surge`, `$loon`, `$argument`,
`$task`, `$prefs`, `$option`, `$input`, `$rocket`, `$axios`, `$app`, `$exit`,
`$log`, `$resource`, `$substore`, `$response`, `$request`, `$trigger`,
`$intercept`, `$wifi`, `$storage`, `$mock`, `$msg`, `$openURL`, `$copy`,
`$browser`, `$chavy`, `$nobyda`, `$eval` — **все отсутствуют**.
Есть только: `$httpClient`, `$persistentStore`, `$notification` (метод `post`),
`$utils`, `$network`, `$script` (`name`, `startTime`, `type`), `$environment`,
`$done`, `$cronexp`.

Именно отсутствие `$httpAPI` и `$config` одновременно закрывает тему управления
политиками из скрипта: в Surge это делает первый, в Loon — второй.

## 3. МЕХАНИКА ДИАГНОСТИЧЕСКОГО СТЕНДА

### 3.1 Схема перебора нестабильного API
Падение внутри прослойки не ловится `try/catch` и убивает прогон целиком.
Поэтому проверки идут **по одному шагу за прогон**:

1. состояние лежит в `ctx.storage` под ключом `rh_scan` (ревизия k4-7) или
   `rh_scan8` (ревизия k4-8): `{ rev, reset, cursor, results }`;
2. **курсор сдвигается ДО выполнения шага** и сразу записывается;
3. шагу присваивается метка `НАЧАТ И НЕ ЗАВЕРШЁН — шаг роняет прогон`;
4. после успеха метка заменяется результатом.

Если шаг роняет прослойку, метка остаётся уликой, а следующий прогон продолжает
со следующего шага. Именно так был пойман `$httpClient.request`.
Сброс перебора — сменить значение `env.RH_RESET`.

### 3.2 Параметры, передаваемые скрипту через `env`
`RH_POST_URL` (адрес приёма отчёта, с токеном), `RH_GROUP`, `RH_GROUP2`,
`RH_NODE` (первый обычный узел из подписки), `RH_NODE2` (первый явно объявленный),
`RH_TEST_URL`, `RH_HEAVY` (тяжёлые замеры, по умолчанию `0`), `RH_RESET`.

**Токен в текст скрипта не попадает** — только через `env`. Сам текст отдаёт
Worker по `/t/<token>/script/k4.js`, а не `raw.githubusercontent.com`: под
whitelist raw недоступен, а свой origin и так единая точка отказа.

### 3.3 Приём отчётов
`POST /t/<token>/probe?key=kN` → ключ `probe:<kN>` в стендовой D1.
Хранятся последние **20** прогонов, тело ограничено **64 КБ**.
Просмотр — `GET` того же адреса, параметр `&n=1` отдаёт только последний прогон
(без него выгрузка становится неподъёмной для пересылки).

### 3.4 Версионирование
Ревизия скрипта (`K4_REV`) ведётся **отдельно от версии Worker'а** — правка проб
не требует перезаливки Worker'а, скрипт подтягивается по `update_interval: 300`.
Тот же приём в боевом контуре называется `PANEL_REV`.

## 4. РАЗБОР ПОДПИСКИ В `proxies`

Перенос `vless://` в профиль: `name`, `server`, `port`, `user_id`, `flow`
(только `xtls-rprx-vision`), `transport`.
Транспорт: `security=reality` → `tls{sni}` + `reality{public_key, short_id}`;
`security=tls` → `tls{sni}`; `type=ws` → `ws{path, headers{Host}}`.
**`fp` (fingerprint) из ссылки не переносится** — в документации Egern такого
поля нет, а угадывать нельзя (профиль падает на первой ошибке типа).

Две тонкости, которые легко упустить:

1. **Имена явных узлов намеренно не совпадают с именами из подписки**
   (`RH-Явный-1..3`). Узлы подписки дедуплицируются **по имени**, и совпадение
   сделало бы результат проверки неоднозначным — непонятно, чей узел отвечает.
2. **Percent-encoding имён в подписке непоследователен** — часть имён закодирована,
   часть нет. Поэтому `decodeURIComponent` всегда в `try`, иначе разбор падает на
   первом же неполном имени.

Состав подписки на 2026-08-07: 69 узлов — 43 `[VPN]`, 4 `[🌀 VPN]`, 5 `[Игры]`,
17 `[Обход - <оператор>]`; транспорт 52 tcp + 17 ws, gRPC нет.
Замечание: в более позднем прогоне справочник фиксирует 68 узлов и 51 в пуле —
состав подписки меняется, считать всегда из `sub_cache`, не из памяти.

## 6. ИНФРАСТРУКТУРНЫЕ ГРАБЛИ (не про Egern, но ломают работу)

1. **Workers Builds не даёт выбрать ветку при создании проекта.** Первая сборка
   идёт из ветки по умолчанию: стенд был задеплоен боевым кодом с биндингом на
   боевую базу. Лечение — Settings → Build → Branch control → production branch,
   галочку «Builds for non-production branches» держать снятой. Проверять итог
   не по логу сборки, а запросом к эндпоинту.
2. **Мусор в хвосте файла при коммите.** Случалось трижды подряд, сборка падала.
   Защита — **хвостовой страж**: файл заканчивается строчным комментарием без
   перевода строки, и дописанный хвост попадает внутрь комментария. После push
   всегда проверять хвост и импортировать модуль.
3. **Обратные слэши в тексте скрипта, живущем в шаблонной строке.** `\d`
   превращается в `d` и **тихо ломает регулярки**. Все классы символов писать
   явно: вместо `\d` — `[0-9]`, вместо `\s` — пробел.
4. **`raw.githubusercontent.com` кэширует ~5 минут.** Сверять по коммиту
   (`/<sha>/<файл>`), а не по ветке, иначе видно старое.
5. **Лимиты Cloudflare free — на аккаунт целиком**: D1 100 000 строк в сутки,
   Workers 100 000 запросов в сутки. Стенд ест ту же квоту, что боевой контур.

## 7. ЧТО ЧЕСТНО НЕ ПРОВЕРЕНО

- `smart` и `priorities` на живом трафике (K5), `conditional` по SSID/BSSID.
- Виджеты и `generic`-скрипт — как выглядит и что реально показывает.
- `http_request`/`http_response`-скрипты и перехват без MITM.
- `prev_hop` (цепочки) — и, главное, **как их тарифицирует Lastdep**.
- `ctx.ssh` — не с чем соединяться.
- Модули (`modules`, `env_schema`, `compat_arguments`).
- Своя настройка DNS в профиле.
- Звонки (K6), TikTok, поведение под реальным whitelist (K1, K3).
- Требует ли скриптинг Pro-версии — признаков ограничения не встретилось,
  но прямой проверки не было.
