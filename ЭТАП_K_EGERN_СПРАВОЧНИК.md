# ЧАСТЬ I. ОФИЦИАЛЬНАЯ ДОКУМЕНТАЦИЯ

## 1. Устройство конфига

Конфиг — один YAML-файл. Корневые разделы:

| Раздел | Зачем |
|---|---|
| `proxies` | узлы, объявленные прямо в конфиге |
| `policy_groups` | группы политик (7 типов) |
| `rules` | правила маршрутизации |
| `dns` | DNS-подсистема |
| `scriptings` | скрипты (5 типов) |
| `widgets` | виджеты iOS |
| `modules` | подключаемые модули (аналог плагинов Loon) |
| `mitm`, `http_captures` | расшифровка и запись HTTP |
| `url_rewrites`, `header_rewrites`, `body_rewrites`, `map_locals` | переписывание трафика |
| `auto_update` | самообновление профиля по ссылке |
| глобальные поля | `ipv6`, `block_quic`, `bypass_tunnel_proxy`, `real_ip_domains`, `proxy_latency_test_url`, `direct_latency_test_url`, `close_connections_on_policy_change`, `include_all_networks`, `compat_route` |

**ПОРЯДОК ПРАВИЛ (ДОК).** Правила проверяются СВЕРХУ ВНИЗ в порядке записи;
первое совпавшее выигрывает, остальные не смотрятся. В отличие от Loon здесь
НЕТ правила «доменные раньше IP» — только порядок в файле.

## 2. УЗЛЫ (`proxies`)

Поддерживаемые протоколы (ДОК): HTTP, SOCKS5, Shadowsocks, Trojan, Hysteria2,
Vless, Vmess, WireGuard.

### Поля vless
`name` (глобально уникальное), `server`, `port`, `user_id`, `flow`, `tfo`,
`udp_relay`, `transport`, `block_quic`, `prev_hop`, `ip_version`.

`ip_version`: `dual_stack` (по умолчанию), `v4_only`, `v6_only`, `v4_prefer`, `v6_prefer`.

### `transport` — РОВНО ОДИН КЛЮЧ
Ключи: `http1` | `http2` | `tls` | `wss` | `ws` | `grpc`.

| Ключ | Смысл | Поля |
|---|---|---|
| `tls` | просто TLS | `sni`, `skip_tls_verify`, `fingerprint_sha256`, `reality{public_key, short_id}` |
| `wss` | WebSocket **поверх TLS** | `path`, `headers{Host}`, `sni`, `skip_tls_verify` |
| `ws` | WebSocket **без TLS** | `path`, `headers{Host}` |
| `grpc` | gRPC (TLS всегда) | `service_name`, `sni`, `user_agent` |
| `http1`/`http2` | маскировка под HTTP | `method`, `path`, `headers` |

**Reality лежит ВНУТРИ `tls`, а не рядом.**
`fingerprint_sha256` — это отпечаток СЕРТИФИКАТА сервера, а НЕ маскировка uTLS
(параметр `fp` из ссылки подписки в Egern не переносится — аналога нет).

### `prev_hop` — ЦЕПОЧКИ ПРОКСИ
Поле есть и у узла, и у группы. Путь трафика: телефон → предыдущий узел →
текущий узел → цель. **В Loon такого нет.**

## 3. ГРУППЫ ПОЛИТИК (`policy_groups`)

Семь типов: `select`, `auto_test`, `smart`, `fallback`, `load_balance`,
`external`, `conditional`. Встроенные политики: `DIRECT`, `REJECT`.

### Общие поля пяти базовых типов
`name`, `policies`, `flatten`, `filter`, `urls`, `update_interval`, `block_quic`,
`icon` (SF Symbols или URL), `hidden`, `prev_hop`, `latency_test_url`.

- **`urls` и `filter` есть У ВСЕХ пяти типов**, не только у `external`.
  Значит подписку можно вешать прямо на `smart` или `fallback`.
- Можно смешивать: статические `policies` + подписка `urls`. Узлы подписки
  встают ПОСЛЕ статических и дедуплицируются по имени.
- `filter` всегда применяется к узлам из `urls`; к статическим — только вместе с `flatten`.
- `latency_test_url` у группы главнее глобальных настроек.

### По типам

| Тип | Поведение | Свои поля |
|---|---|---|
| `select` | ручной выбор | — (тест задержки только вручную из UI) |
| `auto_test` | самый быстрый по задержке | `interval` (600), `tolerance` (100 мс), `timeout` (5 с, макс 60) |
| `smart` | умный выбор по EWMA | `priorities` |
| `fallback` | первый живой по порядку | `interval` (600), `timeout` (5 с, макс 60) |
| `load_balance` | размазывание трафика | `algorithm`: `hash` (по умолчанию) или `round_robin` |
| `external` | устаревшая форма подписки | `type` + всё выше; `policies`/`flatten` НЕ работают |
| `conditional` | выбор по сети | `rules` (ssid/bssid/cellular), `default_policy` |

### `smart` — это наш рейтинг внутри приложения (ДОК)
Учитывает задержку, джиттер и надёжность; сглаживает случайный шум через EWMA;
учитывает боевые сбои, а не только пробы; переключается с гистерезисом и
минимальным временем удержания; частота проб адаптивная.
**Коэффициенты внутри НЕНАСТРАИВАЕМЫ.** Единственный рычаг — `priorities`:
regex по имени → коэффициент. `<1` повышает шансы, `>1` понижает,
`0` — всегда первым. Правила смотрятся по порядку, первое совпавшее выигрывает.

### `conditional` — разделение Wi-Fi/сотовой без скриптов
Правила трёх видов с glob-масками: `ssid` (имя Wi-Fi), `bssid` (MAC роутера),
`cellular` (тип сети: `NR`, `NRNSA`, `LTE`, `WCDMA`, `HSDPA`, `HSUPA`, `CDMA`,
`eHRPD`, `EDGE`, `GPRS`). Первое совпавшее выигрывает, иначе `default_policy`.
Наши данные уже известны: SSID `fh_862d68_5G`, BSSID `c4:64:b6:86:2d:6c`.

## 4. ПРАВИЛА (`rules`)

### Доменные
`domain` (точно), `domain_suffix` (по границе точки), `domain_keyword`,
`domain_regex`, `domain_wildcard` (glob, без учёта регистра).

### IP
`geoip`, `ip_cidr`, `ip_cidr6`, **`asn`** (номер или название организации,
например `AS13335` или `Telegram Messenger Inc`).

### Прочие
`url_regex`, `user_agent`, `dest_port` (одиночные/диапазоны/смешанно:
`80,443,8000-9000`), `protocol` (`tcp`, `udp`, `http`, `https`, `quic`, **`stun`**),
`rule_set`.

### По сетевому окружению — ПРЯМО В ПРАВИЛАХ
**`ssid`, `bssid`, `cellular`** — это НЕ только типы группы `conditional`, но и
полноценные типы правил. То есть маршрут может зависеть от того, дома ли
телефон. **В Loon этого нет** (там только `ssid-trigger` на весь режим).

### Логические
`and`, `or`, `not` — вложенные подусловия любого типа.

### Поля правила
`match`, `policy`, `name` (для логов), `no_resolve`, `disabled`.

### Наборы правил (`rule_set`)
Внутри набора все условия по ЛОГИЧЕСКОМУ ИЛИ. Доступные множества:
`domain_set`, `domain_keyword_set`, `domain_suffix_set`, `domain_regex_set`,
`domain_wildcard_set`, `geoip_set`, `ip_cidr_set`, `ip_cidr6_set`, `url_regex_set`,
`asn_set`, `user_agent_set`, `ssid_set`, `bssid_set`, `cellular_set`,
`protocol_set`, `dest_port_set`, `and_set`, `or_set`, `not_set`.

**Совместимость (ДОК + ПРОВЕРЕНО):** Egern принимает наборы правил в формате
Surge/Shadowrocket — конвертация не нужна.

## 5. DNS

Два независимых пути разрешения:
- **Default DNS** — для трафика пользователя, идёт через `forward`.
- **Proxy DNS** — для разрешения адресов самими прокси; всегда напрямую
  (иначе была бы зацикленность DNS → прокси → DNS).

Порядок: `hosts` → `forward` → умолчание → фильтр `block_ips`.

| Поле | Зачем |
|---|---|
| `bootstrap` | стартовый DNS, только UDP:53, всегда напрямую; значение `system` подмешивает системные |
| `upstreams` | именованные группы серверов; внутри группы гонка, побеждает быстрейший |
| `forward` | правила маршрутизации запросов по группам |
| `hosts` | ручное сопоставление имён и IP, glob-маски |
| `proxy_nameservers` | жёсткий DNS для прокси, обходит `forward` |
| `block_ips` | вырезать адреса из ответов (анти-подмена) |
| `public_ip_lookup_url` | периодически узнаёт внешний IP и подставляет его в ECS |
| `skip_tls_verify` | только для самоподписанных |

Протоколы: UDP, DoT (`tls://`), DoH (`https://`), DoQ (`quic://`), DoH3 (`h3://`).

**В `forward` есть `ssid` / `bssid` / `cellular`** — разный DNS дома и в дороге.
Кэш сопоставления сбрасывается при смене сети. Значение `reject` — отказ в запросе.

## 6. СКРИПТЫ (`scriptings`)

Пять типов:

| Тип | Когда срабатывает | Свои поля |
|---|---|---|
| `http_request` | перед отправкой запроса | `match` (regex по URL), `body_required`, `binary_body`, `max_size` |
| `http_response` | после получения ответа | то же |
| `schedule` | по cron | `cron` (5 или 6 полей) |
| `generic` | вручную / как источник виджета | — |
| `network` | при смене сетевого окружения | — |

Общие поля: `name`, `script_url` (удалённый или локальный), `env`,
`update_interval` (86400), `timeout` (по умолчанию 10 с, **максимум 600**), `disabled`.

Форма файла: `export default async function (ctx) { ... }`.

**ВАЖНОЕ ПРОТИВОРЕЧИЕ В ДОК.** Про `network`-скрипты написано, что они годятся
·«for automatically switching proxy nodes». НО в справочнике JS API НЕТ НИКАКОГО
метода для смены политики (см. часть III, пункт 1). Либо это рекламная фраза,
либо где-то есть неописанный механизм. **Кандидат на поиск лазейки.**

## 7. JAVASCRIPT API (`ctx`) — ПОЛНЫЙ СОСТАВ

| Объект | Что даёт |
|---|---|
| `ctx.script.name` | имя скрипта |
| `ctx.env` | переменные из конфига |
| `ctx.app` | `version`, `language` |
| `ctx.device` | `cellular{carrier, radio}`, `wifi{ssid, bssid}`, `ipv4{address, gateway, interface}`, `ipv6`, `dnsServers` |
| `ctx.cron` | cron-выражение (только в schedule) |
| `ctx.widgetFamily` | размер виджета (только в generic) |
| `ctx.request` / `ctx.response` | тело и заголовки (только в http-скриптах) |
| `ctx.http` | get/post/put/delete/head/options/patch |
| `ctx.storage` | `get`, `set`, `getJSON`, `setJSON`, `delete` |
| `ctx.notify(...)` | уведомление |
| `ctx.lookupIP(ip)` | `{country, asn, organization}` |
| `ctx.compress` | gzip/gunzip/deflate/inflate/brotli/unbrotli |
| **`ctx.ssh`** | **SSH-клиент с SFTP** |
| `ctx.respond(...)` / `ctx.abort()` | ответить самому / оборвать запрос |

### `ctx.http` — параметры запроса
`headers`, `body`, `timeout`, **`policy`** (через какой узел/группу идти),
`policyDescriptor`, `redirect` (`follow`/`manual`/`error`), `credentials`
(`omit`/`include`), `insecureTls`.

### `ctx.notify` — богаче, чем кажется
`title`, `subtitle`, `body`, `sound`, `duration`, `attachment{url | base64, mimeType}`,
`action{type: "openUrl" | "clipboard", url, text}`.
То есть пуш может нести **картинку** и по тапу открывать ссылку или копировать текст.

### `ctx.ssh` — самая неожиданная возможность
Подключение: `host`, `port`, `username`, `password` или `privateKey`, `passphrase`, `timeout`.
- `session.exec(command)` → `{code, stdout, stderr}` — выполнение команд на сервере;
- `session.sftp()` → полноценные файловые операции: `readFile`, `writeFile`,
  `appendFile`, `readdir`, `mkdir`, `rm`, `stat`, `chmod`, `chown`, `rename`,
  `symlink`, `realpath`, `statfs`.

## 8. ВИДЖЕТЫ (`widgets`)

`generic`-скрипт возвращает JSON-описание, Egern рисует его как виджет iOS.
Связка: `widgets: - name: ... script_name: ... env: ...`.

Размеры: `systemSmall`, `systemMedium`, `systemLarge`, `systemExtraLarge`,
`accessoryCircular`, `accessoryRectangular`, `accessoryInline` (последние три —
экран блокировки).

Элементы: `widget` (корень), `stack` (контейнер row/column), `text`, `image`,
`spacer`, `date` (самообновляемое время).

Свойства: `url` (открыть по тапу — в том числе deep link), `opacity`, `width`,
`height`, `flex`, `padding`, `gap`, `backgroundColor`, `backgroundGradient`,
`backgroundImage`, `borderRadius`, `borderWidth`, `borderColor`, `shadow*`,
`refreshAfter` (когда обновиться).

**Картинки**: `sf-symbol:<имя>`, base64-растр, и главное — **встроенный SVG**
(`data:image/svg+xml,<svg ...>`). Значит графики скорости и шкалы рисуются
вектором прямо из скрипта, без картинок с сервера.

## 9. МОДУЛИ (`modules`)

Аналог плагинов Loon. Модуль может содержать: `dns`, `rules`, `url_rewrites`,
`header_rewrites`, `body_rewrites`, `map_locals`, `scriptings`, `mitm`,
`http_captures`, `widgets`, `bypass_tunnel_proxy`, `real_ip_domains`.

**Модуль НЕ может содержать узлы и группы политик** — так же, как в Loon.
НО в отличие от Loon правила модуля, судя по ДОК, НЕ ограничены
`DIRECT`/`REJECT`/`PROXY` — про такое ограничение ничего не сказано.
**НЕ ПРОВЕРЕНО** — если подтвердится, можно вынести в модули гораздо больше,
чем было возможно в Loon.

### `env_schema` — аналог `[Argument]` из Loon
Модуль объявляет свои настройки, и Egern **сам рисует для них элементы в UI**:
- `options: ["true","false"]` → тумблер;
- другие `options` → выпадающий список;
- без `options` → поле ввода.
Плюс `name`, `description`, `default_value`.

### `compat_arguments` — подстановка `{{{ИМЯ}}}`
Значения подставляются при разборе модуля. Строковые поля — в кавычках,
числовые — без. Опасно: значение с кавычкой, слэшем или переводом строки
ломает YAML.

### Приоритет переменных
**Модуль > Виджет > Скрипт.**

## 10. MITM, ЗАПИСЬ HTTP, ПЕРЕПИСЫВАНИЕ

- `mitm.hostnames` — что расшифровывать (нужен установленный корневой сертификат).
- `http_captures` — что **записывать**. Форматы: простой список или
  `includes` / `excludes`. Глобально включается в UI: `All → … → Enable Global
  HTTP Captures`.
- `url_rewrites`, `header_rewrites`, `body_rewrites`, `map_locals` — переписывание
  адресов, заголовков, тела и подмена ответов локальными данными.

## 11. URL-СХЕМЫ (`egern:/...`)

Все поддерживают `x-success=` для возврата в вызвавшее приложение.

| Схема | Действие |
|---|---|
| `egern:/start` / `egern:/stop` | включить / выключить VPN |
| `egern:/profiles/new?url=&name=` | добавить профиль |
| `egern:/policy_groups/new?...` | добавить группу |
| `egern:/subscriptions/new?url=` | добавить подписку |
| `egern:/rules/new?type=&match=&policy=` | добавить правило |
| `egern:/modules/new?url=&name=` | добавить модуль |
| **`egern:/connections`** | **открыть список соединений** |
| `egern:/connections/<id>` | открыть конкретное соединение |

**Нет схемы для смены выбранного узла в группе** — только добавление новых сущностей.

## 12. СОВМЕСТИМОСТЬ С SURGE

Официально (FAQ): Egern принимает **наборы правил Surge** и **модули Surge**.
Это объясняет то, что мы нашли в поле (часть II, пункт 6): внутри среды
скриптов живёт неописанная прослойка Surge.

Также в введении упомянуты, но нигде не описаны подробно:
- **локальный HTTP-прокси и SOCKS5-прокси серверы**;
- **синхронизация конфига между устройствами через iCloud**;
- подробное логирование TCP, UDP, DNS и HTTP.

# ЧАСТЬ II. ЧТО МЫ ПРОВЕРИЛИ САМИ

> Устройство k3, Egern 2.20.0, iOS 18.7. Подробности — `ЭТАП_K_ШАГ_4.4_РЕЗУЛЬТАТЫ.md`.

## 1. Профиль и группы — РАБОТАЮТ
Профиль, собранный нашим Worker'ом, принят. Фильтры по имени работают:
`^(?!.*Обход)` → 51 узел, `\[Обход` → 17 при 68 в подписке.

## 2. «Слабый DIRECT» — ПЕРЕНОСИТСЯ (проверка K2)
Egern принимает `DIRECT` членом `fallback` и тестирует его ГРУППОВЫМ
`latency_test_url`: 36 мс против таймаута на заведомо недостижимом 192.0.2.1.
Значит вся наша модель обхода РКН работает.

## 3. Списки правил — БЕЗ ПЕРЕДЕЛКИ (проверка K7)
Шесть наших списков загрузились, политики совпали с ожидаемыми,
включая Shadowrocket-формат.

## 4. Скрипты по расписанию — РАБОТАЮТ БЕЗ MITM (проверка K4)
`schedule`-скрипт исполняется, `ctx.http` с `policy` маршрутизуется, отчёт
`POST`'ом доходит до Worker'а. Расшифровка трафика не нужна.

## 5. ПОУЗЛОВАЯ АДРЕСАЦИЯ — РАБОТАЕТ (главный вопрос)
Узел из подписки по имени в `policy` даёт 404. **Но узел, ОБЪЯВЛЕННЫЙ
в `proxies`, адресуется по имени.** Доказано тремя способами:

| Способ | Результат |
|---|---|
| три узла → `cdn-cgi/trace` | три разных выхода, групповой выход отличен от всех трёх |
| четыре политики → `ifconfig.me` | четыре разных адреса |
| замер 256 КБ через три узла | 8,3 / 7,4 / 1,2 Мбит/с — скорость привязана к узлу |

Страна в имени узла совпала с фактической (RU и DE).
**Следствие: персональный спидтест переносится.**

## 6. Среда скриптов — ПОЛНЫЙ WEBKIT + ПРОСЛОЙКА SURGE
Скрипт выполняется в настоящем браузерном движке (`AppleWebKit/605.1.15`,
`location` = `http://egern-js/`).

Есть и работает: `WebSocket` (проверен эхо-сервером), `localStorage`
(переживает прогоны), `indexedDB`, `Worker`, `EventSource`, `RTCPeerConnection`,
`WebAssembly`, `XMLHttpRequest`, `Blob`, `FormData`, `structuredClone`, `Intl`.

Дополнительно есть НЕОПИСАННЫЙ слой совместимости с Surge 5.8.3:
`$httpClient`, `$persistentStore`, `$utils` (geoip/ipasn/ipaso/ungzip), `$network`,
`$script`, `$notification`, `$done`, `$cronexp`, `$environment`.
`$persistentStore` и `ctx.storage` — ОДНО хранилище.

Замеры: `ctx.storage` держит 1 МБ на ключ; миллион итераций — 7 мс;
5 параллельных запросов — 109–211 мс; gzip 576 → 36 байт, brotli → 26.

## 7. Разбор всех транспортов — ПОДТВЕРЖДЁН
`tls`, `tls` + `reality`, `wss` — все приняты. ws-узел дал свой выход
(95.213.184.49) при расходе в один запрос обходного трафика.

## 8. Локальный сервер Egern — ТОЛЬКО РАЗДАЧА СКРИПТОВ
`__context.baseUrl` = `http://localhost:13991/js`. Перебор через `DIRECT`:
`/js` и `/js/` → 200 (пустое тело); `/`, `/api`, `/v1`, `/config`, `/policies`,
`/status`, `/version` → 404. Без `policy: DIRECT` запрос уходит в туннель.
Ранее проверены и пусты: 9090, 8080, 6152, 6170, 7890, 1082, 8888.

## 9. ПЛАВАЮЩИЕ ВЫХОДНЫЕ АДРЕСА — ВАЖНО ДЛЯ БОЕВОГО КОНТУРА
Один и тот же узел за полчаса меняет выходной IP (у одного — даже сеть целиком).
А Cloudflare ОТКАЗЫВАЕТ части выходных адресов: `cp.cloudflare.com` и
`www.cloudflare.com` дают 400, а `speed.cloudflare.com` и всё остальное через
тот же узел — 200.

Подбор замены (через проблемный узел и контрольный):

| URL | Проблемный узел | Контрольный |
|---|---|---|
| `cp.cloudflare.com/generate_204` | **400** | 204 |
| `www.msftconnecttest.com/connecttest.txt` | 200 | 200 |
| **`www.gstatic.com/generate_204`** | **204** | **204** |
| `captive.apple.com/hotspot-detect.html` | 200 | 200 |
| `ifconfig.me/ip` | 200 | 200 |

**Это касается и боевого Loon**: там `proxy-test-url` — тот же
`cp.cloudflare.com/generate_204`. Живой быстрый узел может выглядеть мёртвым,
и из-за плавающих адресов это плавающая проблема.

## 10. Геобазы на устройстве — НЕНАДЁЖНЫ
Для узлового IP `ctx.lookupIP` и `$utils.geoip` дают `PK` без ASN, а Cloudflare
говорит `RU`. Для `8.8.8.8` те же функции отвечают правильно.
**Страна узла — только из имени.**

# ЧАСТЬ III. ЧТО НЕ РАБОТАЕТ И ГРАБЛИ

## 1. Переключение политики из скрипта — НЕТ НИКАКОГО СПОСОБА
Нет `$config` (Loon), нет `$httpAPI` (Surge), нет аналога в `ctx`,
локальный сервер только раздаёт скрипты, URL-схемы умеют только добавлять.
Для RouteHub терпимо: выбор делает `fallback`/`smart`, не скрипт.

## 2. Выгрузки записей трафика НЕТ (проверка K9)
Смотреть в приложении можно, выгрузить файлом — нет.

## 3. `$httpClient` игнорирует `node` и `policy`
Запрос идёт по обычным правилам. Адресует ТОЛЬКО `ctx.http`.
А `$httpClient.request` **роняет весь прогон** — не вызывать.

## 4. Глобальный `fetch` идёт МИМО туннеля
Политикам не подчиняется. Всё — через `ctx.http`.

## 5. `crypto.subtle` ОТСУТСТВУЕТ
Есть только `getRandomValues`. SHA-256 и HMAC на устройстве штатно не считаются
— важно для наших токенов и подписей.

## 6. Падение внутри прослойки НЕ ловится `try/catch`
Убивает весь прогон. Отсюда схема «один шаг за прогон, курсор в хранилище».

## 7. Профиль проверяется по типам и падает на ПЕРВОЙ ошибке
Отвергается весь файл целиком. Замеченные случаи: `hijack_dns` — список,
а не булево; `transport` — ровно один ключ. Новые конструкции вводить ПО ОДНОЙ.

## 8. Сcron нормализуется
`*/5 * * * *` превращается в `0 */5 * * * *`. Интервал должен превышать самый
долгий шаг, иначе прогоны перекрываются и портят состояние.

## 9. `ctx.widgetFamily` пуст в `schedule`
Как и `ctx.request`/`ctx.response` — заполняются только в своих типах.

## 10. `sessionStorage` не переживает прогон
Живёт в пределах одного запуска. Состояние — только `ctx.storage` и `localStorage`.

## 11. Перечисления ключей хранилища нет
Имена ключей надо знать заранее.

## 12. Экран запуска скриптов малоинформативен
При ручном запуске не видно ни прогресса, ни итога. Лечится уведомлениями
из самого скрипта (сделано в ревизии k4-10).

# ЧАСТЬ IV. НЕИСПОЛЬЗОВАННЫЕ ВОЗМОЖНОСТИ — ГДЕ ИСКАТЬ ЛАЗЕЙКИ

> Всё ниже — из официальной документации, НО НАМИ НЕ ПРОВЕРЕНО
> и НИГДЕ НЕ ИСПОЛЬЗОВАНО. Самое перспективное — в начале списка.

## 1. `ctx.ssh` — SSH и SFTP ПРЯМО С ТЕЛЕФОНА
Скрипт может зайти на сервер по SSH, выполнить команды и читать/писать файлы.
Зачем может пригодиться: полноценное хранилище вместо Worker'а; архив
измерений без лимитов Cloudflare; канал управления, когда Worker недоступен
под whitelist. Требует своего сервера — у нас его сейчас нет.

## 2. `prev_hop` — ЦЕПОЧКИ УЗЛОВ
Трафик через ДВА узла подряд. **Потенциально решает главную боль по
обходному трафику**: обходной узел первым хопом (платный, но пробивает
whitelist), обычный вторым — если платным считается только трафик выходного
узла, схема может удешевить работу под блокировкой. Требует проверки и
сверки с тарификацией провайдера.

## 3. Правила `ssid` / `bssid` / `cellular`
Разные маршруты дома и в дороге **на уровне отдельных правил**, а не всего
режима. Можно запретить обходные узлы дома одной строчкой. Это то, чего нам
не хватало на Этапе E.

## 4. `smart` + `priorities`
Готовый рейтинг узлов внутри приложения. Через `priorities` можно задать
наш региональный приоритет regex'ами по именам узлов. Коэффициент `0`
(«всегда этот первым») — возможная замена нашей sticky-логике для ИИ.

## 5. `ctx.notify` с `action` и `attachment`
Пуш может открывать ссылку по тапу, копировать текст в буфер и нести
картинку (в том числе base64, то есть сгенерированную на ходу).

## 6. Виджеты с встроенным SVG
Графики скорости, шкалы, индикаторы — вектором прямо из скрипта, без сервера.
Виджет на экране блокировки (`accessory*`) — состояние без разблокировки.

## 7. `env_schema` в модулях
Тумблеры и списки в интерфейсе приложения без всякого кода — то, что в плане
было задумано через `[Argument]` Loon.

## 8. `egern:/connections` — обход отсутствующего журнала?
Список соединений открывается ссылкой, а виджеты и пуши умеют открывать ссылки.
Выгрузки это не даёт, но быстрый доступ — да.

## 9. `http_captures` с `includes`/`excludes`
Запись HTTP по выборке доменов. Вместе с `http_response`-скриптом может
частично заменить отсутствующую выгрузку журнала: скрипт сам шлёт что видел.
Ограничение: только HTTP/HTTPS и только с MITM.

## 10. `public_ip_lookup_url` в DNS
Приложение само периодически узнаёт внешний IP. Может быть полезно для
детектора блокировки и для отслеживания тех самых плавающих адресов.

## 11. `map_locals` и `ctx.respond`
Ответить на запрос своими данными, не ходя в сеть. Потенциально — локальная
панель прямо на телефоне по выдуманному адресу (как `rh.box` в Loon).

## 12. Синхронизация через iCloud
Упомянута во введении. Могла бы дать раздачу конфига между устройствами
без Worker'а вообще. Подробностей в документации НЕТ.

## 13. Локальные HTTP и SOCKS5 серверы
Упомянуты во введении, параметров в документации нет.

## 14. Локальные файлы вместо ссылок
`script_url`, `urls` групп и `rule_set` принимают **локальные пути**.
Значит часть контура может работать без сети вообще — важно под whitelist.

## 15. `flatten` + `filter` на статических группах
Можно разворачивать вложенные группы в плоский список узлов и тут же фильтровать
— упрощает нашу схему с десятком групп.

## 16. Противоречие в документации про `network`-скрипты
Сказано, что они годятся для «автоматического переключения узлов», хотя API
для этого не описано. **Либо ошибка в документации, либо скрытый механизм.**
Стоит спросить авторов напрямую.

## 17. Правила внутри модуля без ограничения политик
В Loon правила плагина могли ссылаться только на DIRECT/REJECT/PROXY.
В документации Egern такого ограничения НЕТ. Если подтвердится — всю
маршрутизацию можно вынести в отключаемые модули.

## 18. `and_set` / `or_set` / `not_set` в наборах правил
Логика внутри выносимого файла — то есть сложные условия можно генерить
Worker'ом и обновлять без переимпорта профиля.

## 19. `insecureTls` и `fingerprint_sha256`
Закрепление сертификата узла — защита от подмены на уровне провайдера.

## 20. `refreshAfter` у виджета
Скрипт сам решает, когда его следующий раз разбудить — возможный второй таймер
помимо cron.
