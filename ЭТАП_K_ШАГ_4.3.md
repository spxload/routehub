## 1. ПРАВКА e0.2.3 — ГРУППА `RH-Проба-DIRECT`

### 1.1 Причина
Проверки K1 и K2 сформулированы через член `DIRECT` внутри `fallback`
(K1 — пробивает ли Egern такой член под whitelist, K2 — применяется ли к нему
`latency_test_url`). В профиле e0.2.2 **ни одна группа члена `DIRECT` не
содержала**: `RH-RU` = [`RH-Проба-Обычная`, `RH-Обход`], `DIRECT` из класса B
убран намеренно. То есть проверки не выполнялись не из-за отсутствия whitelist,
а из-за отсутствия предмета проверки.

Вопрос принципиальный: модель «слабый DIRECT» (вывод 2 в `СТАРТ.md`) —
основание маршрутизации класса B в Loon. Переносима она на Egern или нет —
одна из развилок решения «мигрируем / остаёмся».

### 1.2 Что добавлено
```
fallback RH-Проба-DIRECT = [DIRECT, RH-Обход]
                           latency_test_url = http://cp.cloudflare.com/generate_204
                           interval 120, timeout 5
```
Группа **ни одним правилом не используется**: `rules` не менялись, трафик в неё
не попадает, маршрутизация прежняя. Цена ошибки нулевая, единственный расход —
пробы раз в 120 с.

### 1.3 Что наблюдается
Профиль задаёт два разных адреса пробы:

| Поле | Адрес | Достижим из РФ напрямую |
|---|---|---|
| `direct_latency_test_url` (верхний уровень) | msftconnecttest.com | да, всегда |
| `latency_test_url` (у группы) | cp.cloudflare.com | под whitelist — нет |

Различение:
- член `DIRECT` получает результат по **групповому** адресу → модель «слабый
  DIRECT» переносится: под whitelist `DIRECT` отвалится и `fallback` уйдёт
  на обход;
- член `DIRECT` получает результат по `direct_latency_test_url` либо не
  тестируется вовсе → под whitelist `DIRECT` всегда выглядит живым, модель
  **не переносится**, класс B на Egern придётся строить иначе (как и сделано
  сейчас в `RH-RU`).

K2 закрывается наблюдением при обычной сети, K1 — при первом реальном whitelist.
Группа должна стоять на устройстве заранее: whitelist — событие редкое, окно
наблюдения не планируется.

### 1.4 Проверено до импорта
Генератор прогнан YAML-парсером (`js-yaml`, Node 22) в обоих вариантах:
6 групп в объявленном порядке, `RH-Проба-DIRECT` = `["DIRECT","RH-Обход"]`,
7 правил, `default → RH-Главный`. В `&safe=1` группа присутствует без
`latency_test_url` — как и остальные `fallback`. Файл после push сверен
по `raw`: `RE_BYPASS` не удвоился, версия `e0.2.3`.

### 5.1 K7 — вывод
`rule_set` в Egern принимает списки, написанные для Shadowrocket, включая
`domains_banking.list` (misha-tgshv). Фактическая маршрутизация совпала с
ожидаемой: whitelist-домен → `DIRECT`, банковский → `RH-RU`, зарубежный →
`RH-Главный`. Значит набор списков из боевого `C-draft-39` переносится на
Egern без конвертации — существенный аргумент в пользу миграции.

### 5.2 K2 — почему не закрыт
Ping 32–43 мс у члена `DIRECT` доказывает два факта: Egern **принимает**
`DIRECT` внутри `fallback` и **тестирует** его наравне с прочими членами.
Но по величине задержки нельзя сказать, какой адрес использован: и
`cp.cloudflare.com`, и `msftconnecttest.com` — CDN с точками присутствия рядом,
из РФ оба дают десятки миллисекунд. Разрешающего признака в этом наблюдении нет.

Разрешающий тест — заведомо недостижимый адрес пробы. Предложение (решение
за Дианой): вторая диагностическая группа
```
fallback RH-Проба-DIRECT-2 = [DIRECT, RH-Обход]
                             latency_test_url = http://192.0.2.1/generate_204
```
`192.0.2.1` — TEST-NET-1 (RFC 5737), не маршрутизируется в интернете, поэтому
недостижим и напрямую, и через любой узел. Исход бинарный:
- `DIRECT` в этой группе показывает отказ/таймаут → групповой
  `latency_test_url` к члену `DIRECT` **применяется**, модель «слабый DIRECT»
  переносится;
- `DIRECT` продолжает показывать десятки миллисекунд → используется
  `direct_latency_test_url`, модель **не переносится**.

Первая группа (`RH-Проба-DIRECT`) остаётся как контроль. Обе правилами не
используются, маршрутизацию не меняют.

### 5.3 K9 — что найдено на устройстве
Экран «Хранилище» перечисляет занятый объём по категориям (кэш, журналы и
прочее) и не даёт ни просмотра записей, ни выгрузки файла. Формулировка
проверки K9 («экспорт записей трафика») этому экрану не соответствует.
Открытый вопрос: существует ли выгрузка в другом месте приложения (экран
запросов / Analytics — действие «поделиться», «экспортировать»). Если нет,
K9 закрывается отрицательно, и следствие серьёзное: наблюдаемость на Egern
ограничена экраном устройства, данные наружу не отдаются, а значит вопрос
о разморозке локального дашборда возвращается в повестку решения по миграции.
