# Доказать, что заблокировано

ЗАЧЕМ. В RouteHub «невозможно» не раз оказывалось «не нашли»: запрос через
конкретный узел в Stash (`X-Stash-Selected-Proxy`), журнал доменов без MITM
(`/connections` → `host`), скрипт под whitelist (override с `payload`).
И наоборот, «работает» оказывалось случайностью: RH-RKN месяцами детектил
потому, что `$httpClient` молча игнорировал имя ГРУППЫ. Ложное «нельзя»
закрывает направление навсегда — поэтому вывод дорогой, и платить за него
проверкой дешевле, чем потерянной возможностью.

Урок: «не нашли в документации» ≠ «нет»; «не сработало один раз» ≠ «не
работает»; «сработало» ≠ «работает правильно».

## Чек-лист

- [ ] **1. Утверждение точно.** ЧТО не работает, на каком клиенте и версии,
  в какой сети (Wi-Fi/сотовая), при включённом ли whitelist РКН, через какой
  узел, дата. Не знаешь сеть и whitelist — запросить прогон пробы L10
  (кнопка RH-L10), не гадать. Пример: «`git push` не работает» → точнее
  «push из сессии без репозитория в источниках отклонён прокси с текстом
  „not in this session's authorized repository set“» — и это уже не
  «баг #76248», месяц считавшийся причиной.

- [ ] **2. Ступень на лестнице доказательств** (назвать явно):
  1. документация молчит;
  2. документация прямо запрещает;
  3. один отказ на устройстве;
  4. воспроизводимый отказ ≥3 раз в разных условиях, с контролем;
  5. отказ + понятная причина + положительный контрольный опыт рядом.
  «Невозможно» — только со ступеней 4–5. Ступени 1–3 — «не удалось, не
  доказано». Тот же порядок и для «работает / действует»: `?timeout=` у
  `/proxies/{name}/delay` ядро молча игнорирует — «параметр действует»
  годился бы только после опыта, где разные значения дают разное поведение.

- [ ] **3. Контрольный опыт рядом с отрицательным.** Тот же прибор на
  заведомо рабочей цели должен показать «да». Нет контроля — прибор мог
  быть сломан. Примеры: ST14 — свой короткий тайм-аут пробы четырежды
  выдавал живой узел за мёртвый; ST15 — `gemini.google.com/robots.txt`
  показывал «доступно», а запрет живёт на уровне аккаунта, отказ проба не
  видела по построению; `null` метрики читался как лучшее значение.
  Проверить: прибор видит ИМЕННО тот отказ, о котором вывод?

- [ ] **4. Не меньше 5 альтернативных путей до вывода.** Вызвать роль
  `ideator` (передать утверждение из п. 1, что пробовали, ступень). В
  списке обязательны: недокументированные поля и параметры (перебор полного
  объекта, как нашлись `$httpClient.globalProxy`, порт 13991 Egern,
  `getSubPolicys`), чужой клиент как донор, побочный канал (журнал,
  заголовок, `$persistentStore`), простое (единицы, свой тайм-аут, опечатка
  в имени узла — полное имя, URL-кодированное).

- [ ] **5. «Не умеем» ≠ «нельзя».** Записать три списка: что проверено (с
  условиями), что не проверено, следующий дешёвый шаг. Если хоть один путь
  из п. 4 не проверен — вывод «не умеем пока», а не «нельзя».

- [ ] **6. Закон.** Ни один шаг проверки не гоняет трафик через обходные
  узлы (правило 1) и не пишет в маршрутизацию (правило 2). Проверка,
  требующая этого, не делается — это ограничение метода, а не довод «за»
  невозможность.

- [ ] **7. Запись.** В память проекта (`claude/ПАМЯТЬ_ПРОЕКТА.md` в Файлах
  проекта; нет доступа — строкой в ответе для координатора):
  `<дата> · <утверждение из п. 1> · ступень N · контроль: … · не проверено:
  … · следующий шаг: …`. Нашёлся путь позже — у старой записи пометка
  «ОПРОВЕРГНУТО <дата>: <как>», запись не удалять.

## Формат вывода в ответе

Одна строка вердикта: «доказано (ступень 4–5)» / «не доказано (ступень
1–3), не умеем пока» — затем утверждение, контроль, число проверенных путей
и следующий шаг. Без простыней.
