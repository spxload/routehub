## 1. ПЕРЕПОСТАНОВКА K4

Исходная формулировка («скрипт на `http_request` без MITM») била мимо цели.
Документация (`/docs/configuration/scriptings`) даёт **пять** типов скриптов:

| Тип | Запуск | Зависит от перехвата |
|---|---|---|
| `http_request` | перед отправкой запроса | да |
| `http_response` | после получения ответа | да |
| **`schedule`** | по cron (5 или 6 полей) | **нет** |
| `generic` | вручную, привязан к виджету | нет |
| `network` | при смене сетевого окружения | нет |

Телеметрия и спидтест RouteHub строятся на `schedule`, то есть **MITM не нужен
вовсе**. Проверять надо не «работает ли скрипт без MITM», а какие именно
возможности JS API пригодны к переносу.

Общие поля всех типов: `name`, `script_url` (локальный путь или удалённая
ссылка), `env` (пары ключ-значение → `ctx.env`), `update_interval` (по умолчанию
86400), `timeout` (по умолчанию 10 с, **максимум 600 с**), `disabled`.

Форма скрипта: `export default async function (ctx) { … }`.

## 2. ЧТО ДАЁТ JS API (из документации, до проверки на устройстве)

| Возможность | Egern | Loon |
|---|---|---|
| запрос через политику | `ctx.http.get(url, { policy, policyDescriptor, timeout, headers, body, redirect, insecureTls })` | `$httpClient.get({node})` |
| хранилище | `ctx.storage.get/set/getJSON/setJSON/delete` | `$persistentStore` |
| сеть устройства | `wifi.ssid`, `wifi.bssid`, `cellular.carrier`, `cellular.radio`, `ipv4.address/gateway/interface`, `ipv6`, `dnsServers` | только `ssid` |
| гео по IP | `ctx.lookupIP(ip)` → `{country, asn, organization}` | `$utils.geoip/ipasn/ipaso` |
| уведомления | `ctx.notify` с `attachment` и `action` (`openUrl`/`clipboard`) | `$notification.post` |
| сжатие | `ctx.compress.gzip/gunzip/deflate/inflate/brotli/unbrotli` | нет |
| SSH/SFTP | `ctx.ssh.connect` | нет |
| таймаут скрипта | до 600 с | 200 с |
| параметры из профиля | `env` → `ctx.env` | `[Argument]` |

**Не найдено в документации:** управления выбором внутри группы политик
(аналога `setSelectPolicy`). Для RouteHub некритично — выбор делает `fallback`
(вывод 1 в `СТАРТ.md`), — но пробел фиксируется.
**Не подтверждено:** требует ли скриптинг Pro-версии. Признаков ограничения в
документации нет; выяснится на устройстве.

## 3. ЧТО ПРОВЕРЯЕТ ДИАГНОСТИЧЕСКИЙ СКРИПТ

Один `schedule`-скрипт, каждая проба в своём `try/catch`: отказ одной не
прекращает остальные, в отчёт идёт текст ошибки. Результат уходит `POST`'ом на
стенд и дублируется в `ctx.storage`.

| # | Проба | Что доказывает |
|---|---|---|
| P1 | сам запуск, `ctx.script.name`, `ctx.cron` | `schedule` работает без MITM — ядро K4 |
| P2 | `ctx.env` | параметры из профиля доходят до скрипта (замена `[Argument]`) |
| P3 | `ctx.app.version`, `ctx.app.language` | фиксация версии Egern из самого приложения |
| P4 | все поля `ctx.device` | какие непусты; `bssid` и `carrier` в Loon недоступны |
| P5 | `storage`: строка, JSON, удаление, счётчик прогонов, запись 32 КБ | персистентность между прогонами и предел размера значения |
| P6 | `GET cp.cloudflare.com/generate_204` без `policy` | базовая работоспособность `ctx.http` |
| P7 | то же с `policy: "RH-Пул-Обычные"` | запрос через **группу** |
| P8 | то же с `policy: "DIRECT"` | принимается ли встроенная политика строкой |
| P9 | то же с `policy: "<имя узла>"` (передаётся через `env`) | **запрос через КОНКРЕТНЫЙ УЗЕЛ** — фундамент спидтеста |
| P10 | `POST` отчёта на стенд | телеметрия доходит до Worker; снимает остроту K9 |
| P11 | `GET http://192.0.2.1/` с `timeout: 3000` | форма отказа: исключение или объект со статусом |
| P12 | `ctx.lookupIP` для 8.8.8.8 и для внешнего IP, полученного через узел | пригодность к определению страны выхода на устройстве |
| P13 | `ctx.compress.gzip` → `gunzip` | пригодность к сжатию телеметрии |
| P14 | `ctx.notify` — один раз при первом успешном прогоне | канал оповещений |
| P15 | скачивание 1 МБ через обычный узел, замер Мбит/с | пригодность к спидтесту; **по флагу `env`, не каждый прогон** |

**Через `RH-Обход` не идёт ни одна проба** — трафик платный. Ограничение
жёсткое, в коде отдельной проверкой.

## 4. РЕШЕНИЯ ПО РЕАЛИЗАЦИИ

1. **Текст скрипта отдаёт сам стенд** по токен-защищённой ссылке
   `GET /t/<token>/script/k4.js?key=kN`, а не `raw.githubusercontent.com`.
   Причина: под whitelist `raw` недоступен, а свой origin — и так единая точка
   отказа; вторую заводить незачем. Правка скрипта = деплой Worker'а, без
   ожидания кэша GitHub (~5 мин).
2. **Токен в скрипт не зашивается**: адрес приёма отчёта передаётся через
   `env.RH_POST_URL`, который Worker подставляет при генерации профиля.
3. **Приём отчётов** — `POST /t/<token>/probe?key=kN` → ключ `probe:<kN>` в
   стендовой D1, хранится последние 20 прогонов. Просмотр — `GET` того же пути.
4. **Частота на время проверки** — `cron: "*/5 * * * *"`, по решению Дианы
   временно; после закрытия K4 переводится на разумный интервал.
5. **Тяжёлая проба P15** — по флагу `env.RH_HEAVY`, по умолчанию выключена;
   включается отдельным прогоном, чтобы не гонять по мегабайту каждые 5 минут.
6. **Имя узла для P9** Worker берёт из `sub_cache` — первый узел, попадающий
   под `RE_NORMAL`. Обходные исключены по построению.
7. Боевой контур не затрагивается, ветка `egern` в `main` не сливается.

## 5. КРИТЕРИЙ ЗАКРЫТИЯ K4

K4 закрыт положительно, если прошли P1, P6, P7, P10 — то есть `schedule`-скрипт
исполняется, `ctx.http` работает, запрос через группу маршрутизируется и отчёт
доходит до Worker'а. P9 отдельно определяет судьбу спидтеста: без запроса через
конкретный узел персональные метрики скорости на Egern невоспроизводимы, и это
самостоятельный аргумент в решении о миграции. Прочие пробы — сведения, а не
условия.
