# ADR-01: Схема контуров — один Worker и одна база или несколько

**Статус:** Принято (Диана, 2026-08-16) — вариант В плюс Secrets Store
**Дата:** 2026-08-16
**Решает:** Диана

## Контекст

Сейчас на каждого клиента заводится отдельный контур: своя ветка, свой Worker,
своя база D1, свой ключ устройства. Схема отработана на Egern, 16.08 по ней же
заведён стенд Stash.

Цена этой схемы всплыла сразу: у каждого нового Worker'а секреты
(`SUBSCRIPTION_URL`, `SUB_HWID`, `ADMIN_KEY`) задаются заново руками в
дашборде, а код Worker'а дублируется по веткам и расходится.

**Проверенные факты, на которых строится решение** (Cloudflare docs, 16.08):

1. **Secrets Store** — аккаунтские секреты, открытая бета, до 100 на аккаунт.
   Один секрет биндится к нескольким Worker'ам. Это снимает «вписывать заново»
   независимо от того, один у нас Worker или пять.
2. **Wrangler environments + Workers Builds.** Штатная схема: один репозиторий,
   одна ветка, в `wrangler.toml` секции `[env.<имя>]`, деплой-команда
   `npx wrangler deploy --env <имя>`. Из одной ветки разворачивается несколько
   отдельных Worker-сервисов.
3. **Квоты D1 — аккаунтские, а не на базу:** 5 млн чтений строк в сутки,
   100 000 записей, 5 ГБ суммарно по всем базам. Разделение на базы квоты не
   экономит и не увеличивает. Лимит на *количество* баз в документации не нашёл —
   не могу подтвердить.
4. **Workers Free:** 100 Worker'ов на аккаунт, 100 000 запросов в сутки,
   5 cron-триггеров на аккаунт. Текущий расход — сотни запросов в сутки.

Из пункта 3 следует, что довод «одна база экономит лимиты» неверен. Значит
вопрос о базе — только про изоляцию и риск.

## Решение

Принят **вариант В**: одна кодовая база в `main` с модулями по клиентам,
несколько Worker-сервисов через `[env.*]`, базы D1 остаются раздельными,
секреты выносятся в Secrets Store.

## Рассмотренные варианты

### А. Оставить как есть (ветка + Worker + база на клиента)

| Измерение | Оценка |
|---|---|
| Сложность | Низкая на старте, растёт с числом клиентов |
| Стоимость | Ручное заведение секретов на каждый контур |
| Риск | Минимальный: контуры не пересекаются нигде |
| Поддержка | Тяжёлая: код расходится по веткам, правку надо повторять |

**За:** боевое не может пострадать от стенда — ни кодом, ни данными.
**Против:** каждый новый клиент — повторение всей ручной процедуры; общий код
живёт в трёх ветках и неизбежно расходится (уже видно на `egern`).

### Б. Один Worker + одна база с разделением по клиентам

| Измерение | Оценка |
|---|---|
| Сложность | Средняя: роутинг по клиенту, префиксы ключей в `kv` |
| Стоимость | Секреты один раз, деплой один |
| Риск | **Высокий** |
| Поддержка | Лёгкая: один комплект файлов |

**За:** секреты и деплой один раз, код общий, сущностей меньше.

**Против:**
- Боевой контур и стенд делят один рантайм и одну версию. Ошибка в
  клиентском модуле стенда роняет Loon — а стенд по определению место, где
  ломают.
- Общая база возвращает проблему, из-за которой базы и разделили: реестр
  устройств хранит `nonce`, и ошибка в префиксе ключа перепривязывает боевые
  k1/k2 (вывод 12). Изоляция дешевле разбора последствий.
- Экономии по квотам нет (факт 3), то есть главный аргумент за общую базу
  отсутствует.

### В. Один код, несколько Worker-сервисов, базы раздельные

| Измерение | Оценка |
|---|---|
| Сложность | Средняя разово: перенос модулей + правка `wrangler.toml` |
| Стоимость | Секреты один раз (Secrets Store), деплой автоматический |
| Риск | Низкий: рантаймы и данные изолированы |
| Поддержка | Лёгкая: правка общего модуля разъезжается по всем контурам |

Устройство: `main` содержит `src/*` (общее ядро) и `src/clients/{loon,stash}.js`
(клиентская часть — формат конфига и особенности). `wrangler.toml`:

```toml
name = "routehub"                      # боевой
[env.stash]
name = "routehub-stash"
[[env.stash.d1_databases]]
binding = "RH_DB"
database_name = "routehub-stash-db"
```

Деплой-команда стенда в дашборде — `npx wrangler deploy --env stash`.
Ветки `stash` и `egern` после переноса становятся не нужны.

**За:** снимает обе жалобы (секреты, дублирование кода), сохраняя изоляцию.
**Против:** правка общего ядра затрагивает все контуры сразу — нужна
дисциплина: сначала прогон тестов, потом деплой стенда, потом боевого.
Обновление боевого Worker'а перестаёт быть «отдельным делом».

## Трейд-офф

Спор идёт между **удобством сопровождения** и **радиусом поражения ошибки**.

Вариант Б покупает удобство ценой того, что стенд получает доступ к боевому
рантайму и боевым данным — то есть ровно того, ради чего стенды и отделяли.
Вариант В покупает то же удобство, отдавая взамен только общий код: ошибка в
общем модуле действительно доедет до боевого, но она доедет и сейчас — потому
что модуль всё равно копируется между ветками, просто вручную и с задержкой.

Отдельно: объединение баз в текущей ситуации не даёт ничего. Ни лимитов, ни
удобства — только риск. Этот пункт отклонён.

## Последствия

**Станет легче:** заводить нового клиента (ветка не нужна, нужен `[env.*]` и
база); держать ядро в одном месте; секреты не переписывать.

**Станет тяжелее:** дисциплина деплоя — правка ядра требует прогона тестов и
осознанного порядка выкатки. Понадобится пометка в коде, какой клиент активен
(`[vars] CLIENT = "stash"`), и ветвление в точке входа.

**Придётся пересмотреть:** если у стенда появится своя разрушительная логика
(например, запись в чужие ключи), вернуться к варианту А для него конкретно.

## Шаги реализации (вариант В принят 16.08)

Сделано в тот же день: `[env.stash]` добавлен в `wrangler.toml` ветки `main`,
проверен `wrangler deploy --dry-run` в обоих окружениях (боевое видит
`routehub-db`, стенд — `routehub-stash-db`), cron у стенда отключён явно
(`crons = []`). Заметка: команду деплоя боевого воркера в дашборде стоит
перевести на `npx wrangler deploy --env=""`, чтобы верхний уровень выбирался
явно, а не по умолчанию.
