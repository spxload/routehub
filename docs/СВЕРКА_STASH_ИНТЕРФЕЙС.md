## 1. ГЛАВНОЕ: два закрытых вопроса

### 1.1. Порядок узлов в группе — наш механизм работает

Проект влияет на выбор узла **только порядком** внутри группы. Документация
Stash говорит, что по умолчанию действует «порядок конфигурационного файла»,
но тут же упоминает переключение на «сортировку по результатам замера», не
уточняя, меняется ли при этом логика выбора или только вид списка. Это был
риск, отменяющий весь подход.

**Найдено два органа управления, оба стоят в нашу пользу:**

| Где | Что | Состояние |
|---|---|---|
| Настройки → Подробнее → «Настройка» | Тумблер **«Сортировать прокси по задержке»**. Подпись: «Сортировать прокси в группе политик по результатам проверки соединения: прокси с низкой задержкой будут располагаться первыми» | **ВЫКЛЮЧЕН** |
| Вкладка «Группы прокси», меню вверху справа | **«Метод сортировки»**: «Порядок в файле конфигурации» / «Результаты теста производительности» | **«Порядок в файле конфигурации»** |

**Вывод:** порядок из нашего конфига соблюдается.

**Риск, который надо держать в чек-листе:** это настройки **приложения**, а не
конфигурации. Worker их не контролирует и не видит. Случайное переключение
любого из двух тихо обнулит сортировку по композитному баллу — маршрутизация
при этом продолжит работать, просто выбор станет чужим. При разборе любой
жалобы вида «стал ходить не через тот узел» проверять эти два места первыми.

**Чего проверка НЕ доказала:** формулировка «располагаться первыми» описывает
расположение в списке. Влияет ли включённый тумблер на выбор члена группой
`fallback` — по интерфейсу сказать нельзя. Пока тумблер выключен, вопрос
академический.

### 1.2. Профиль против провайдера — механизм обязан жить в провайдере

Настройки → Ресурсы → «Файл конфигурации»: **интервал обновления 12 (часов)**,
автообновление включено. Подпись дословно:

> «Интервал в часах для обновления файла конфигурации с удалённого источника,
> **пока приложение Stash работает на переднем плане**. Для тихого обновления
> правил и прокси в фоновом режиме, когда VPN включён, используйте **набор
> правил и поставщика прокси**».

**Вывод:** профиль подтягивается только при открытом приложении, и даже тогда
раз в 12 часов. Держать в нём порядок узлов бессмысленно — он протухнет.
Порядок и метрики уходят в `proxy-providers` с коротким интервалом; профиль
остаётся статическим каркасом (группы, правила, DNS, ссылка на провайдера).

Косвенное подтверждение из демо-конфига (`Default.yaml`, строки 1–7):
секция `proxy-providers` со значением `interval: 600` — то есть 600 секунд
у самого разработчика в примере.

## 3. ПОПРАВКИ К ПРЕЖНИМ ЗАПИСЯМ ПРОЕКТА

### 3.1. У Stash ЕСТЬ нативный тест скорости — запись «нет» неверна

Инструменты → Диагностика → **«Тест скорости»**: поле «Исходящий» (на снимке
`DIRECT`), выбор сервера, метрики — расстояние, задержка, пропускная
способность загрузки, байт загрузки, пропускная способность отдачи, объём
загруженных данных; кнопка «Начать». Подпись: «Тест скорости предоставляется
сторонними сервис-провайдерами, и компания Stash Network Limited не несёт
ответственности за доступность».

Рядом — **iPerf3**: хост, порт 5201, режим реверса, непрерывный режим,
встроенный локальный сервер iPerf3.

**Но источником метрик он нам не станет, по трём причинам:**

1. ручной и поштучный — ни цикла, ни расписания, один исходящий за раз;
2. льёт настоящий трафик к внешнему серверу; прогон через обходной узел
   нарушает жёсткое правило 1 проекта (платный трафик);
3. признаков выгрузки нет: ни один из 29 перебранных путей контроллера
   (замеры ST3–ST4) не отдавал результатов, в интерфейсе экспорта не видно.
   Утверждать, что API нет вовсе, оснований нет — но и подтверждений нет.

**Где он полезен:** разовая ручная калибровка. Прогнать один узел нативным
тестом и нашим спидтестом и сравнить. Проект уже знает, что тест-адрес меняет
результат вчетверо (`speed.cloudflare.com` 2,1 против `proof.ovh.net`
22,7 Мбит/с на том же узле), так что независимая точка отсчёта ценна. Для
чистой пропускной способности iPerf3 подходит лучше.

### 3.2. Задержку Stash меряет сам — половина спидтеста может не понадобиться

Настройки → Сеть → **«Тест подключения: HTTP HEAD»**. Подпись: «Укажите метод
тестирования Stash для определения задержки прокси-узла. Результаты,
полученные разными методами, могут значительно различаться, а некоторые
протоколы прокси могут не поддерживать измерение скорости TCP».

Это механизм за `GET /proxies/{имя}/delay` контроллера. Плюс у каждой группы
есть «Периодическое тестирование, интервал тестирования 600» и «Ленивый режим»
(«в ленивой группе тестирование выполняется только при её использовании»).

**Отсюда деление задачи:**

| Метрика | Кто мерит |
|---|---|
| Задержка (`rtt`, `med`) | **Stash сам**; метод фиксируется настройкой «Тест подключения» |
| Скорость (`down`), джиттер (`jit`), буфер (`bl`) | **Мы сами**, скриптом — нативной замены нет |

Не проверено: совпадает ли `delay` ядра с нашим `rtt` по порядку величины на
живом узле. Это открытый вопрос 10 стенда, и от него зависит, писать ли
пинг-часть спидтеста под Stash вообще.

### 3.3. У групп есть «Допуск» (tolerance) — в вики не нашлось

Редактор группы типа `URL Test`, раздел «Параметры»: **«Допуск»**, значение 0.
Подпись: «Если разница между результатами теста двух прокси превышает
допустимое значение, будет выбран тот, у которого результат ниже».

Прежняя сверка по вики параметр не находила. Для нас прямого применения нет
(выбор делает порядок, а не url-test), но запись «tolerance у Stash нет»
неверна.

## 4. ГРУППЫ: ЧТО ВИДНО В РЕДАКТОРЕ

**Типов ровно пять**, из всплывающего меню «Выберите тип группы прокси»:
`URL Test`, `Select`, `Load Balance`, `Fallback`, `Relay`.

**Общие поля любой группы:** Имя, Тип, Значок (URL картинки), «Скрыть из
списка», Примечание.

**Членство задаётся четырьмя независимыми источниками сразу** (раздел
«Включить прокси и группы»):

- «Включить прокси и группы» — явный список имён;
- **«Включить поставщиков прокси»** — узлы из провайдера;
- «Включить прокси из URL» — узлы прямо по ссылке;
- «Включить все прокси» — тумблер;
- **«Фильтр с регулярными выражениями»**.

Подпись: «Группа прокси может содержать несколько прокси, групп прокси и
поставщиков прокси».

**Это важно для нас:** явный список имён и провайдер сосуществуют в одной
группе. Значит схема «провайдер даёт описания узлов, группа задаёт порядок
именами» интерфейсом не запрещена. **Проверить на стенде**: сохраняется ли
при этом наш порядок и не схлопывает ли Stash один узел, стоящий в двух
группах в разном порядке (пункт 2 чек-листа ADR-02).

**Параметры по типам:**

| Тип | Особые поля |
|---|---|
| `URL Test` | Допуск; Периодическое тестирование (интервал 600, ленивый режим) |
| `Select` | **«Политика SSID»** — «Автоматически переключать прокси в зависимости от состояния сети (SSID Wi-Fi или мобильные данные)» |
| `Load Balance` | Стратегия (`consistent-hashing` / `round-robin`) |
| `Relay` | URL теста производительности, тайм-аут теста производительности |

`Политика SSID` у `Select` — подтверждение ADR-02 на уровне интерфейса.

## 5. УЗЛЫ И ПОСТАВЩИК

**Поддерживаемые типы прокси** (экран «Тип прокси»): DIRECT, HTTP, SOCKS5,
Shadowsocks, Snell, Trojan, **AnyTLS**, Hysteria, Hysteria2, TrustTunnel, TUIC,
Juicity, WireGuard, SSH, **VLESS**, VMess, StashLink, tailscale, Mieru, Reject.

**Поля узла** (редактор «Прокси»): Имя, Примечание, Тип прокси; «Тест
производительности» — **URL теста производительности** и **тайм-аут теста
производительности** (по умолчанию 5); «Базовая сеть» — **прокси дозвона**
(`dialer-proxy`, может ссылаться на прокси или группу) и **имя сетевого
интерфейса** (например `en0`), взаимоисключающие.

Подпись про тест: «Прокси, у которых во время теста задержки истекло время
ожидания, будут помечены как "нездоровые". Если прокси используется
несколькими групповыми политиками, **результаты теста для этого прокси будут
общими между этими группами**».

**Поставщик прокси** (редактор): Имя, URL, **Интервал обновления**, Фильтр
регулярных выражений, плюс блок **«Переопределить параметры теста
производительности»** — URL и тайм-аут «для прокси в этом поставщике, вместо
использования параметров по умолчанию».

**Для нас:** тест-адрес `connectivitycheck.gstatic.com` задаётся один раз на
уровне провайдера, а не по узлу. Это снимает необходимость писать его в каждое
описание узла.

## 6. ПРАВИЛА, ПЕРЕЗАПИСЬ, СЦЕНАРИИ

**Редактор правила:** Тип правила (на снимке `DOMAIN`), Содержимое, Политика,
плюс параметры **«Не разрешать имя хоста»** и **«Скрыть соединение»**,
Примечание.

**Удалённый набор правил:** Имя, URL, **Поведение** (`domain` / `ipcidr` /
`classical`), Интервал, Формат.

**Базовая перезапись** — меню «Добавить»: изменение URL, изменение заголовка,
изменение тела, **имитация изменения** (mock).

**Сценарий (скрипт):** Имя, **Тип** — только `HTTP-запрос` / `HTTP-ответ`;
Регулярное выражение; тайм-аут (10); «Требуется тело»; **«Максимальный размер
тела»** со списком 1 КБ … 2 МБ, по умолчанию 1 МБ; **«Параметры»** —
«Аргумент, передаваемый скрипту во время выполнения. Это строка»; «Двоичный
режим» («тело передаётся скрипту как `Uint8Array`, а не как строка»).

**Поставщик сценариев:** Имя, URL, интервал (3600).

**Замечание:** в этом редакторе типов скрипта только два — HTTP-запрос и
HTTP-ответ. Плитки и cron-задачи заводятся в других местах (секции `tiles` и
`cron` конфига), в визуальном редакторе их нет.

## 8. ТУННЕЛЬ, СЕТЬ, ВНЕШНИЙ ДОСТУП

**Туннель:** «Скрыть логотип VPN»; **«Режим только туннель»** (включён) —
«отключает прокси Stash, заставляя все HTTP(S)-запросы обрабатываться Stash
TUN»; «Режим совместимости туннеля»; **«Режим Tun Stack: Stash»**;
«Маршрутизация туннеля IPv6» (выключена); «Пропустить прокси»
(`10.0.0.0/8, 100.64.0.0/10 … +25`); «Пропустить маршрут туннеля» (… +11);
«Включить все сети» (выключено) с подпунктами «локальные сети», «APNs»,
«сотовые службы».

**Сеть:** «Гибридная сеть» (Wi-Fi и сотовая одновременно, выключена);
**«Прерывать соединения»** — «закрывать соединения при переключении на
прокси-группу типа SELECT», **выключено**; «Тест подключения: HTTP HEAD»;
«Режим параллельных подключений» (включён) — «подключаться ко всем IP-адресам,
если у домена несколько записей A/AAAA, и выбрать самое быстрое»;
«Резервный DNS».

**«Прерывать соединения» важно:** при перевыдаче порядка узлов вопрос «рвутся
ли живые соединения» частично управляем этим тумблером, и по умолчанию не
рвутся.

**Внешний доступ:** «Разрешить устройства LAN» (выключено, порт HTTP и SOCKS
**7890**); «Разрешить внешнее управление» (выключено), «Секрет API» с кнопкой
«Сменить секрет API». Подпись: «Аутентификация через HTTP-заголовок
`Authorization: Bearer ${secret}`».

**Действие:** секрет API попал в переписку на снимке — сменить кнопкой в этом
же разделе. Пробы читают его из `$environment['controller-authorization']` и
подхватят новый сами.

## 11. ЧТО ОСТАЛОСЬ НЕПРОВЕРЕННЫМ

Интерфейс на эти вопросы не отвечает, нужен прогон на стенде:

1. Сохраняется ли порядок узлов, пришедших **из провайдера**, внутри группы,
   и можно ли перечислить их именами в `proxies` при `use:` на тот же
   провайдер.
2. Переваривает ли Stash один узел, стоящий в двух группах в разном порядке
   (пункт 2 чек-листа ADR-02).
3. Срабатывает ли `ssid-policy` при уходе на сотовую (пункт 1 чек-листа).
4. Совпадает ли `GET /proxies/{имя}/delay` с нашим `rtt` по порядку величины.
5. Какие ЗНАЧЕНИЯ принимает `processPath` в `/connections` (первый шаг ADR-03).
6. Есть ли у нативного теста скорости хоть какой-то программный доступ.
7. Как часто провайдер реально перечитывается при `interval: 600` и рвутся ли
   при этом соединения.

## 12. КРАТКО ДЛЯ ТЕХ, КТО ЧИТАЕТ ПЕРВЫЙ РАЗ

- Порядок узлов из нашего конфига Stash соблюдает; два тумблера могут это
  отменить, оба сейчас выключены — проверять их при разборе жалоб.
- Узлы отдаём **поставщиком прокси** с коротким интервалом, профиль — только
  каркас: он обновляется раз в 12 часов и лишь при открытом приложении.
- Задержку Stash меряет сам; скорость и джиттер по-прежнему на нас.
- Нативный тест скорости — ручной инструмент для калибровки, не источник
  метрик.
- Вывод скриптов пишется в файлы «Журналы сценариев» — удобнее буфера обмена.
