## 1. ✅ Спидтест меряет не тем адресом, что группы

**Закрыто 16.08, `routehub-speedtest.js` v0.6.3 и `routehub-viewer.js` v0.6.4.**

Было: `PING_URL = 'http://cp.cloudflare.com/generate_204'` в скрипте против
`proxy-test-url = http://connectivitycheck.gstatic.com/generate_204` в конфиге.
Расхождение возникло в C-draft-40, когда адрес групп сменили: `cp.cloudflare.com`
отвечает **400** на часть плавающих выходных адресов узлов, и для `fallback`
это не таймаут, а отказ — живой узел считается мёртвым. Конфиг и шаблон
AI-групп тогда поправили, скрипт замеров остался на старом адресе.

Стало: обе стороны ходят на один адрес. **Проверить через сутки:** сравнить
медианы `rtt` и состав верхушки списка — это покажет, много ли данных портил
Cloudflare.

## 2. ✅ Документы описывают снятые решения

**Закрыто 16.08 таблицей актуальности в `README.md`** — одна правка вместо
плашек в шести файлах. Помечены как устаревшие и 16.08 перенесены в
`docs/archive/`: `ЭТАП_E_ПРОГРЕСС.md`, `ИНСТРУКЦИЯ_ПРОЕКТА.md`,
`ДЛЯ_ДИАНЫ_инструкция_и_промпты.md`, `ЭТАП_D_RESEARCH_ПРОМПТ.md`,

Риск, который это снимает: новый чат читает документ, принимает описанное за
текущее состояние и предлагает откатить уже переделанное.

## 3. EWMA расходится с записанным решением (приоритет 20)

В `routehub-speedtest.js` `EWMA_A = 0.6`; в памяти проекта записано α ≈ 0.2.
У k1 флаг `ewma` выключен — сглаживания нет вовсе, каждый замер перетирает
предыдущий.

После v1.9.7 (отсечение сбойных значений) и v0.6.3 (единый адрес) вопрос стоит
решать на свежих данных: если разброс упадёт, сглаживание может не понадобиться
вовсе. **Ждёт суток замеров.**

## 4. ✅ Нет способа проверить, что деплой доехал

**Закрыто 16.08:** `GET /version` отдаёт `{"worker":"vX.Y.Z"}` без ключа и
токена. Проверка деплоя стала одной командой:

```
curl https://routehub.proton4iker.workers.dev/version
```

## 5. Ветки-архивы (приоритет 15) — нужна рука Дианы

Через API удалять ветки нельзя, только в веб-интерфейсе GitHub
(`Branches` → корзина). Проверено 16.08 — уникальных коммитов нет:

| Ветка | Коммитов, которых нет в `main` | Вердикт |
|---|---|---|
| `panel-qr` | 0 | удалять |
| `worker-v1.9.0` | 0 | удалять |

| `stash` | 2, оба устарели | удалять после проверки билда стенда |
| `egern` | 47 | **оставить** — закрытое исследование |

У ветки `stash` в `wrangler.toml` весь воркер объявлен стендовым
(`name = "routehub-stash"` без окружений) — это противоречит ADR-01. Документ
стенда из неё уже перенесён в `main` в актуальной редакции.

## 6. `handleConfig` не покрыт тестом целиком (приоритет 15)

Тесты проверяют `renderConfig` и `aiBlocks`, но не путь целиком: реестр →
токен → загрузка конфига → рендер → ответ. Например, `conf_ver` пишется по
регулярке `C-draft-\d+`; изменится формат шапки — версия молча перестанет
обновляться.

**Что делать:** один интеграционный тест на `/config` с моком `fetch` —
проверить подставленную базу с токеном, запись `conf_ver` в реестр и
отсутствие плейсхолдеров.

## 7. k2 тянет конфиг, но не шлёт метрики (приоритет 12)

Замер 16.08: у k2 свежий `last_config_ts`, но `last_seen` — 11 августа.
Устройство ходит за конфигом, а `POST /speed` не делает. Причины: скрипт
выключен, ключ после отвязки не привязался заново (`status: free`), либо битый
аргумент. **Спит до выдачи k2 (Этап G).**

## 9. ✅ `dash.js` превращал `jit = null` в 0

**Закрыто 16.08 (v1.9.8).** Было `jit: it.m.jit || 0` — после v1.9.7 это
показывало сбойный замер как идеальный джиттер. Стало
`jit: (it.m.jit == null ? null : it.m.jit)`, как у `bl`.

## 10. ✅ Заливка по одному файлу через API

`git push` из облачной сессии не работает (баг claude-code #76248), каждая
правка идёт через GitHub API с полным содержимым файла.

Полечено: Worker разложен на модули (v1.9.5), тесты — на четыре файла плюс
`harness.js` (v1.9.7), `CHANGELOG.md` разделён 16.08 на действующий (12,7 КБ:
Worker с v1.9.4, конфиг с C-draft-41) и `CHANGELOG_ARCHIVE.md` (16,6 КБ, всё
предыдущее дословно). Было 27,9 КБ одним файлом. Ни одна запись не потеряна —
сверено построчно.

Обходной путь найден 16.08: массовые операции над репозиторием делаются
разовым workflow в GitHub Actions (`workflow_dispatch`) — так была выполнена
раскладка по папкам. Токен MCP не имеет права `workflows`, поэтому файл
workflow создаёт Диана в вебе, запуск — тоже она.
