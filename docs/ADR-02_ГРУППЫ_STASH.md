# ADR-02: Раскладка групп в Stash — как убрать пару `-W`/`-C` и дублирование узлов

Статус: **предложено 2026-08-17**, к принятию после шагов 1–2 на стенде.
Связанные документы: `ADR-01_СХЕМА_КОНТУРОВ.md`, `ЭТАП_K_STASH.md` (пробы
ST1–ST5), `ЭТАП_K_STASH_СТЕНД.md`.

---

## Контекст

В Loon сложилась конструкция из двух костылей, оба вынужденные.

**Костыль 1 — парные группы.** Родительские `select`-группы `RH-AI`,
`RH-АВТО`, `RH-Звонки` держат по два ребёнка: `*-W` для Wi-Fi и `*-C` для
сотовой. Переключает их скрипт `routehub-netwatch.js` типа `network-changed`
(`FLIP_GROUPS` в его шапке). Штатного способа привязать выбор к типу сети в
Loon нет — отсюда скрипт.

**Костыль 2 — дублирование узлов в выдаче `/nodes`.** Композитный балл
считается отдельно по Wi-Fi и по сотовой, а результат замера вписывается
**в имя узла** (` · 21↓ 68ms`). Одно и то же физическое соединение попадает
в подписку двумя строками с разными именами — иначе два набора не построить.
Подписка удваивается, `matchKey` вынужден склеивать имя обратно к базовому.

Оба костыля живут только потому, что клиент не умеет иначе. Stash умеет.

---

## Что именно даёт Stash (наши замеры, не только вики)

| Возможность | Источник | Значение для задачи |
|---|---|---|
| `ssid-policy` у группы `select`, зарезервированные `default` и `cellular` | документация, `proxy-groups` | родитель сам выбирает ребёнка по сети — костыль 1 снимается штатно |
| Раздельные секции `proxies:` (узлы) и `proxy-groups:` (порядок членов) | формат Clash-YAML | один узел может стоять в двух группах в разном порядке — костыль 2 снимается без скриптов |
| `PUT /proxies/{имя}` → 204 через локальный контроллер | **наш замер ST3–ST5** | из скрипта можно менять выбор группы; резервный путь, если `ssid-policy` не подойдёт |
| `$environment['controller-url']`, `['controller-authorization']` | **наш замер ST2**, в документации отсутствуют | скрипт получает адрес и токен контроллера без настройки |
| `$config` в среде **отсутствует** | **наш замер ST2**: ровно шесть `$`-объектов | скрипт Stash **не может прочитать SSID сам** — значит переключение по сети должно быть на стороне конфига, а не скрипта |
| `setTimeout` растягивается (33 с бюджета → 120 с факта) | **наш замер ST5** | логика «померил и сразу переключил» ненадёжна по времени |

Последние две строки решают спор: раз SSID из скрипта не виден, а таймеры
плывут, переключение по сети остаётся конфигу, а не коду.

---

## Рассмотренные варианты

### А. Оставить как в Loon: пара `-W`/`-C` + скрипт-переключатель

Перенести конструкцию один в один, `netwatch` переписать под Stash.

- ➖ Скрипт нужен, но SSID из него не читается (`$config` нет) — пришлось бы
  определять сеть косвенно, по маякам, то есть тратить запросы на каждую
  смену сети.
- ➖ Дублирование узлов остаётся.
- ➕ Ничего не надо переосмысливать.

**Отклонён:** сохраняет оба костыля и добавляет к ним новый — детект сети
без `$config`.

### Б. Один узел, одна группа, скрипт-контроллер выбирает члена

Одна `select`-группа со всеми узлами; cron-скрипт меряет и ставит лучший
через `PUT /proxies/{имя}`. Тип сети становится не нужен вовсе: балл
считается по свежему замеру, а он уже отражает текущую сеть.

- ➕ Оба костыля исчезают, модель предельно простая.
- ➖ Скрипт пишет в боевую маршрутизацию. Проект такого до сих пор не делал
  сознательно: правило «пробы и диагностика никогда не пишут в боевую
  маршрутизацию» появилось не на пустом месте.
- ➖ Cron требует поднятого туннеля; при растянутых таймерах момент
  переключения непредсказуем.
- ➖ Отказ скрипта = отказ маршрутизации. Сейчас отказ скрипта означает лишь,
  что баллы устарели, а трафик всё равно идёт по группам.

**Отклонён на этом этапе.** Возвращаемся к нему, если `ssid-policy` не даст
нужного поведения; тогда он оформляется отдельным ADR, потому что меняет
принцип «клиент решает сам, сервер только считает».

### В. `ssid-policy` на родителях + один узел в двух упорядоченных группах ✅

```yaml
proxies:                      # каждое соединение описано РОВНО ОДИН РАЗ
  - {name: "🇩🇪 Германия", type: vless, ...}
  - {name: "🇫🇮 Финляндия", type: vless, ...}

proxy-groups:
  - name: RH-АВТО-W           # порядок по баллу Wi-Fi
    type: fallback
    proxies: ["🇫🇮 Финляндия", "🇩🇪 Германия"]
  - name: RH-АВТО-C           # порядок по баллу сотовой — ТЕ ЖЕ узлы, другой порядок
    type: fallback
    proxies: ["🇩🇪 Германия", "🇫🇮 Финляндия"]
  - name: RH-АВТО             # родитель: сеть выбирает сам клиент
    type: select
    proxies: [RH-АВТО-W, RH-АВТО-C]
    ssid-policy:
      cellular: RH-АВТО-C
      default: RH-АВТО-W
```

- ➕ **Костыль 1 снят:** `netwatch` больше не переключает группы. Его
  остальные задачи (детект whitelist, heartbeat, флаг догона) переезжают в
  cron-скрипт или в ручную пробу — они не про маршрутизацию.
- ➕ **Костыль 2 снят:** секция `proxies:` содержит каждый узел один раз,
  порядок задаётся списком в группе. Подписка перестаёт быть вдвое длиннее.
- ➕ Ничего не пишет в маршрутизацию: выбор внутри группы делает клиент,
  переключение по сети — тоже клиент.
- ➖ Метрику больше нельзя вписывать в имя узла: имя одно, а замеров два.
  Нужно решить, где её показывать (см. ниже).
- ➖ Порядок членов группы меняется только при перевыдаче конфига, а не
  подписки. Значит перестроение списка по новым баллам требует обновления
  конфига, а не только `/nodes`.

**Принят как основной.**

## Отдельное решение: куда девать метрику из имени

Три варианта, выбирается при реализации `src/clients/stash.js`:

1. **Обе метрики в одном имени:** `🇩🇪 Германия · W 21↓68 · C 7↓96`.
   Дублирования нет, но имя длинное и в узком списке обрежется.
2. **Метрики только в панели** (`web/routehub-dash.html`, плитка Stash).
   Имя чистое. Требует, чтобы панель открывалась легко — а она открывается
   с телефона, так что стоимость невелика.
3. **Метрика текущей сети** — сервер вписывает ту, что соответствует сети,
   о которой сообщило устройство. Возвращает зависимость от того, что
   устройство знает свою сеть, — то есть частично воскрешает костыль.

Предпочтение: **2**, с **1** как запасным. Вариант 3 отклонён по той же
причине, по которой отклонён вариант Б.

---

## Трейд-офф, который мы принимаем

Порядок узлов в Stash перестраивается перевыдачей **конфига**, а не
подписки. В Loon список приезжал в `/nodes` и обновлялся чаще и дешевле.
Значит для Stash `interval` обновления конфига становится тем, что раньше
делал интервал подписки. Это надо померить на стенде: как часто Stash
готов перечитывать конфиг и не мигает ли при этом соединение.

---

## Последствия

- `src/clients/stash.js` собирает **один** список узлов и **три пары**
  упорядоченных групп (AI, АВТО, Звонки) плюс три родителя с `ssid-policy`.
- `routehub-netwatch.js` в контур Stash **не переносится**.
- Ядро (`buildAiTiers`, `scoreOf`, `metricOf`) не меняется вовсе: оно и так
  отдаёт два упорядоченных списка, просто клиентский слой перестаёт
  превращать их в два набора узлов.
- Для Loon всё остаётся как есть: там `ssid-policy` нет, костыли обоснованы.

---

## Что проверить на стенде до принятия

1. `ssid-policy` действительно переключает родителя при уходе на сотовую —
   с телефона, переключением авиарежима Wi-Fi.
2. Один и тот же узел в двух группах в разном порядке не вызывает у Stash
   ни ошибки разбора, ни схлопывания списка.
3. Как часто Stash перечитывает конфиг и рвёт ли при этом соединения.
4. Видно ли имя хоста в `/connections` — от этого зависит, нужен ли журнал
   незагрузившихся доменов отдельным механизмом (ST7, пункт 1).
