# СВЕРКА С ДОКУМЕНТАЦИЕЙ LOON — редакция 2026-08-16

> `ДОКУМЕНТАЦИЯ_LOON_RU.md` в этом репозитории описывает версию **3.3.9**,
> на устройстве стоит **3.5.0 (975)**. Переписывать 42 КБ перевода смысла нет —
> вместо этого здесь сверены те факты, на которых держится наш контур.
> Источник: официальная документация `nsloon.app/en/docs` (разделы Policy,
> Script, Script API), прочитана 2026-08-16.

## Главное: одно расхождение с нашим замером

**Документация утверждает, что `node` в `$httpClient` принимает и группу.**
Дословно (раздел Script API, таблица параметров запроса):

> `node` — Node, policy group, or Loon node description to use

Наш тест **T6 от 2026-06-13** показал обратное: имена ГРУПП игнорируются молча,
работают только имена УЗЛОВ. Именно из-за этого 15.08 был снят `routehub-rkn.js`
(он бил маяки через `RH-Проба-VPN` и `RH-Обход`) и написана проба L10, которая
проверяет только узлы.

Возможные объяснения, в порядке правдоподобия:

1. Поведение изменилось между версией, на которой ставился T6, и 3.5.0.
2. T6 был поставлен на группе, чьё имя содержит кириллицу и дефисы
   (`RH-Проба-VPN`) — не исключено, что дело в разборе имени, а не в
   поддержке групп как таковой.
3. Документация описывает намерение, а не поведение.

**Что это меняет для нас.** Ничего срочного: L10 работает через имена узлов и
будет работать в любом случае. Но если группы всё-таки поддерживаются,
открывается более дешёвая проба — бить в группу и смотреть, кого она выберет.
Проверка на устройстве: `$httpClient.get` с `node: 'RH-Проба-VPN'` против
того же запроса с именем узла, который эта группа сейчас выбрала. Обходные
группы для проверки НЕ использовать — платный трафик.

До проверки в памяти проекта остаётся наш замер, а не документация:
своё измерение весит больше чужого утверждения.

## Что документация подтверждает (наши записи верны)

**Типов групп ровно четыре** — `select`, `url-test`, `fallback`,
`load-balance`. Группы типа `ssid` в Loon нет; параметры: `url`, `interval`,
`max-timeout`, для load-balance ещё `algorithm` (Random / PCC / Round-Robin).
Значит пары `-W`/`-C` плюс `routehub-netwatch.js` — вынужденная мера, а не
наше усложнение.

**Типов скриптов ровно пять:** `http-request`, `http-response`, `cron`,
`network-changed`, `generic`. Это закрывает наш открытый хвост «типы скриптов
кроме generic не проверены»: проверять больше нечего, мы используем три из
пяти, а оставшиеся два — это MITM-скрипты, то есть отдельная задача с журналом
незагрузившихся доменов.

**`network-changed`: при нескольких записях запускается только первая.**
Записано у нас — подтверждено дословно.

**`$config.getConfig()`** возвращает JSON с полями `running_model`,
`all_buildin_nodes`, `global_proxy`, `all_policy_groups`, `ssid`, `final`,
`policy_select`. Значения `running_model`: 0 — глобальный DIRECT, 1 — по
правилам, 2 — глобальный прокси. Всё совпадает с нашими записями.

**`$persistentStore.remove()`** — «Removes **all** local data saved through the
script API». Наша пометка про «чистит ВСЕ данные скрипт-API» верна, и это
по-прежнему повод не вызывать его в боевых скриптах.

**Таймаут `$httpClient` по умолчанию — 5000 мс**, у `http-request` /
`http-response` — 10 секунд. У наших проб таймауты заданы явно.

## Что уточнилось

**Версия.** В примере плагина из официальной документации стоит
`#!loon_version = 3.5.1(978)` — то есть выпущена версия новее той, что стоит у
Дианы (3.5.0/975). Что изменилось между ними — из документации не видно,
changelog в открытом виде не нашёлся. Не могу подтвердить, что обновление
что-то даёт нашему контуру.

**Переключение политики документировано как `$config.getConfig(policyName,
selectName)`** — то есть тот же метод с двумя аргументами, возвращает
`true`/`false`. У нас в записях фигурирует `setSelectPolicy`; оба варианта
существуют в рантайме (мы их описывали по сплошной описи глобалов), но в
документации назван именно этот. На нашу работу не влияет — по правилу 2
проекта пробы вообще не пишут в маршрутизацию.

**`$notification.post` принимает объект `attach`** с полями `openUrl`,
`mediaUrl`, `clipboard`. Мы используем `clipboard` — способ остаётся
единственным каналом выгрузки данных наружу.

**Новые параметры `$httpClient`, которых не было в 3.3.9:**

| Параметр | Что делает | С какой сборки |
|---|---|---|
| `body-base64` | тело запроса как Base64 | 612+ |
| `auto-redirect` | следовать редиректам, по умолчанию `true` | 660+ |
| `auto-cookie` | сохранять и отправлять куки | — |
| `binary-mode` | ответ бинарными данными | — |
| `alpn` | выбор ALPN (`h2`) | — |
| `$request.h2_trailers` / `$response.h2_trailers` | трейлеры HTTP/2 | 927+ |

Для наших проб полезен `auto-redirect: false` — маяки отвечают 204, и
следование редиректам может смазать замер, если провайдер подставит портал.
Сейчас он включён по умолчанию.

## Что осталось непроверенным

- `load-balance` с алгоритмом PCC — на устройстве не пробовали.
- Цепочки узлов (Proxy Chain) — трафик тратится на каждом звене, поэтому
  проверка стоит платного трафика; отложено.
- `resource-parser` и URL-схемы (`loon://…`) — из документации видно, что
  схемы есть (`loon://switch` в примере уведомления), детали не смотрели.
- Что нового в 3.5.1 против 3.5.0.
