# 1. ЧТО ТАКОЕ EGERN, ВЕРСИЯ, ЦЕНА

Egern — сетевой клиент для iOS/macOS/visionOS (разработчик BYTE CROSSING LTD).
Прокси, перехват и модификация трафика, MITM, скрипты, модули, виджеты.

| Параметр | Значение |
|---|---|
| Текущая версия | **2.20.0** (подтверждено британской витриной App Store и трекером mwm.ai) |
| Дата 2.20.0 | британская витрина подписывает «23 Jul»; американская показывала 2.19.0 как свежайшую. **Точную дату подтвердить не могу** — расхождение витрин/кэша |
| Цена | приложение бесплатное, разовая покупка Pro $5.99. **У Дианы Pro куплен** |
| Требования | iOS/iPadOS 16+, macOS 13+ (Apple Silicon), visionOS 1.0+ |
| Русский интерфейс | с 2.10.0 |
| Размер | 49.0 МБ |
| Доступность в App Store РФ | **НЕ ПОДТВЕРЖДЕНО** |

**Egern — не клон Surge.** Свой формат конфигурации (YAML `Profile.yaml`) и
свой API скриптов (`export default async function(ctx)`). Совпадение — в
совместимости на импорте: разбирает Surge-модули, Surge rule-set'ы, полные
конфиги Surge, а с 2.18.0 — **конфиги и плагины Loon**, а также подписки
Clash/mihomo (2.19.0) и Shadowrocket/base64.

## 2.1 Состав 2.20.0

**Новое:** Snell v1–v5; SSH как исходящий прокси; SOCKS5 over TLS;
**gRPC (Gun) транспорт для VMess/VLESS**; REALITY для Trojan/AnyTLS/HTTPS с
постквантовым X25519MLKEM768; пиннинг SHA-256 отпечатка сертификата;
**подписка (`urls`) на любой группе политик** — отдельная `external` не нужна;
round-robin в load balance; `ip_version` на прокси; **опция «закрывать
соединения при смене политики»**; правило `listen_port`; DNS через `tcp://`;
**история профиля** (снимок перед каждой правкой + восстановление в одно
касание); страница «Хранилище» с разбивкой; история уведомлений; SVG в
виджетах; установка CA на другие устройства.

**Улучшения:** **smart запоминает отказы реальных соединений** — узел, который
проходит тест, но не работает, понижается; после failover задержка
перезамеряется. Скрипты получили **много больше параллельных HTTP-запросов —
снят лимит WebView ~6 на хост**. Быстрый отказ при отсутствии сети.
Ошибки профиля указывают на конкретное поле.

**Исправления, важные для нас:** логические правила AND/OR/NOT с
неподдерживаемым подправилом **раньше совпадали со ВСЕМ трафиком** — теперь
такое правило игнорируется целиком; исправлено выпадение `encryption: none`
у VLESS из Clash-подписок; правки профиля и ручное обновление ресурсов теперь
применяются сразу; перехват DNS больше не захватывает не-DNS UDP (SNTP).

# 3. ПОДТВЕРЖДЁННЫЕ ФАКТЫ ПО ДОКУМЕНТАЦИИ

## 3.2 Узлы

Протоколы: Shadowsocks (+obfs, ShadowTLS), Snell v1–v5, Trojan, AnyTLS, VMess,
VLESS, Hysteria2, TUIC, WireGuard, SOCKS5, SOCKS5-over-TLS, HTTP/S, SSH.
У VLESS — **REALITY**, `flow: xtls-rprx-vision`, транспорты ws/wss/http2/**grpc**.
Общие поля узла: `tfo`, `udp_relay`, `ip_version`
(dual_stack / v4_only / v6_only / v4_prefer / v6_prefer), `block_quic`,
пиннинг SHA-256 отпечатка (2.20).

## 3.3 Группы политик

Типы: `select`, `auto_test`, `smart`, `fallback`, `load_balance`, `external`,
`conditional`. Встроенные политики `DIRECT` и `REJECT` допустимы как члены.

**Общие поля** (для пяти базовых типов):
- `policies` — узлы, другие группы, DIRECT/REJECT;
- `urls` — **подписки прямо на группе** (2.20), узлы подписки идут после
  статических и дедуплицируются по имени;
- `filter` — regex по имени; к узлам подписки применяется всегда, к
  статическим — только при `flatten: true`;
- `flatten` — развернуть узлы вложенных групп;
- `update_interval` — обновление подписки (по умолчанию 86400; ≤0 отключает);
- `block_quic`, `icon` (SF Symbols **или URL картинки**), `hidden`;
- `prev_hop` — цепочка прокси (устройство → предыдущий хоп → узел → цель);
- **`latency_test_url` — свой URL проверки на группу**; перекрывает глобальные
  `proxy_latency_test_url` и `direct_latency_test_url`. Для `fallback` и
  `load_balance` это URL **фоновой проверки здоровья**.

Специфика:
- `auto_test` — `interval` (600 по умолчанию), `tolerance` (100 мс).
- `fallback` — перебор по порядку, при отказе следующий, **при восстановлении
  более приоритетного возвращается обратно**.
- `smart` — см. 3.4.
- `load_balance` — Random / PCC / Round-Robin (последний с 2.20).
- `conditional` — правила `ssid` / `bssid` / `cellular` → политика + `default_policy`.
- `external` — `type` (стратегия), `urls`, `filter`, `update_interval`.

**Рекурсивный тест задержки** — поведение по умолчанию: проверка спускается по
дереву вложенных групп до реальных узлов. В меню группы есть одноимённый пункт —
это **ручной запуск замера сейчас**, а не тумблер режима.

## 3.4 Smart-группа — как работает

- Кандидаты оцениваются по **серии раундов проб**, значения сглаживаются **EWMA**.
- Балл композитный: **задержка + джиттер + надёжность** (доля успешных проб).
- **Реальные отказы соединений** понижают узел; после failover задержка
  перезамеряется (усилено в 2.20).
- **Гистерезис**: переключение только при заметном выигрыше и по истечении
  минимального времени удержания.
- **Адаптивная частота проб**: реже при стабильности, чаще после сбоя.
- **Параметры не настраиваются.** Единственная настройка — `priorities`:
  словарь «regex по имени узла → коэффициент», умножается на балл.
  `<1` — поднять, `>1` — опустить, `0` — «всегда первым, при отказе откат».
  Побеждает **первое совпавшее** правило (порядок объявления важен).

Пример:
```yaml
priorities:
  "^\\[VPN\\] 🇳🇱 Ams-3$": 0      # закреплённый узел
  "(?i)🇩🇪|🇳🇱|🇫🇮": 0.85          # Европа предпочтительнее
  "(?i)🇮🇳|🇹🇷|🇦🇪": 1.4           # Индия/Турция/ОАЭ — почти никогда
```

## 3.5 Правила

`domain`, `domain_keyword`, `domain_suffix`, `domain_regex`, `domain_wildcard`,
`geoip` (+`no_resolve`), `ip_cidr`, `ip_cidr6`, `asn`, `url_regex`,
`user_agent`, `dest_port`, `src_port`, `listen_port` (2.20),
`protocol` (tcp/udp/http/https/quic/**stun**), **`ssid`**, **`bssid`**,
**`cellular`**, `rule_set` (+`update_interval`), логические `and`/`or`/`not`,
`default`. Политики: имя любой группы, `DIRECT`, `REJECT`, `REJECT-NO-DROP`.

## 3.6 DNS

Два независимых контура:
- **default DNS** — для пользовательского трафика;
- **proxy DNS** — для разрешения адресатов прокси, соединения **всегда прямые**
  (иначе петля DNS → прокси → DNS).

Порядок разрешения: `hosts` → `forward` → умолчание → `block_ips`.

- `bootstrap` — только UDP/53, всегда напрямую, поддерживает `system`.
  Нужен для разрешения имён шифрованных upstream'ов и как последний резерв.
- `upstreams` — именованные группы; внутри группы серверы гонятся параллельно,
  быстрейший выигрывает. Форматы: UDP, `tls://`, `https://`, `quic://`,
  `h3://`, **`tcp://`** (2.20), плюс спецзначения `bootstrap` и `system`.
- `forward` — правила по типам domain / keyword / suffix / wildcard / regex /
  **proxy_rule_set** / **ssid** / **bssid** / **cellular**. Значение: имя группы,
  конкретный сервер, `bootstrap`, `system` или **`reject`** (пустой ответ =
  блокировка домена на уровне DNS). Кэш совпадений сбрасывается при смене сети.
- `hosts` — глоб-шаблон → IP или домен-алиас, в т.ч. обратное IP → домен.
- `proxy_nameservers` — жёсткий перехват DNS прокси в обход `forward`.
- `block_ips` — вырезание записей (антиподмена); отказ только если вырезаны все.
- `skip_tls_verify` — только для самоподписанных upstream'ов.
- `public_ip_lookup_url` — подстановка ECS, чтобы CDN отдавал ближние адреса.

## 3.7 Скрипты

Пять типов: `http_request`, `http_response`, `schedule` (cron 5 или 6 полей),
`generic` (ручной / движок виджета), `network` (смена сетевого окружения).

Общие поля: `name`, `script_url` (локальный путь или ссылка), `env`,
`update_interval` (86400), **`timeout` до 600 с** (у Loon потолок 200), `disabled`.
Для HTTP-скриптов дополнительно: `match` (regex по URL), `max_size` (1 МБ),
`body_required`, `binary_body`.

Ограничения «network-скрипт срабатывает только у первого» в документации **нет**
(в Loon это было И4).

## 3.8 JavaScript API — полный перечень

`ctx.http` (get/post/put/patch/delete/head/options; опции: `headers`, `body`,
`timeout`, **`policy`**, `policyDescriptor`, `redirect`, `credentials`,
`insecureTls`; ответ: status / headers / body-поток / json() / text() / blob() /
arrayBuffer() / formData()), `ctx.storage` (get/set/getJSON/setJSON/delete),
`ctx.notify`, `ctx.lookupIP`, `ctx.device` (wifi.ssid, wifi.bssid,
cellular.carrier, cellular.radio, ipv4/ipv6, dnsServers), `ctx.env`,
`ctx.script.name`, `ctx.cron`, `ctx.request` / `ctx.response`, `ctx.respond`,
`ctx.abort`, `ctx.compress` (gzip/gunzip/inflate/unbrotli), `ctx.ssh.connect`,
`ctx.widgetFamily`.

`ctx.storage` — **своё** пространство скриптов (аналог `$persistentStore`), к
данным приложения отношения не имеет. `ctx.env` — только чтение параметров
извне (конфиг или `env_schema` модуля).

## 3.9 Виджеты

`generic`-скрипт возвращает JSON-DSL. Элементы: `widget`, `stack`, `text`,
`image`, `date`, `spacer`, `linear` (градиент), **SVG** (2.20).
Семейства: systemSmall / Medium / Large / ExtraLarge и accessory-* (локскрин),
приходят в `ctx.widgetFamily`. Поле `refreshAfter` (ISO 8601) задаёт момент
следующего обновления. Объявление: `widgets: [{name, script_name, env}]`.

## 3.10 Модули

Могут содержать: `dns`, `rules`, `url_rewrites`, `header_rewrites`,
`body_rewrites`, `map_locals`, `scriptings`, `mitm`, `http_captures`,
`widgets`, `bypass_tunnel_proxy`, `real_ip_domains`.
**Не могут:** `proxies` и `policy_groups`.

Ограничения «правила плагина только DIRECT/REJECT/PROXY» (наш И8) в
документации **нет** — поле `policy` описано как имя любой политики.

Настройка: `compat_arguments` с подстановкой `{{{ARG}}}` при разборе и
`env_schema`, из которого приложение **само строит UI**:
`options: ["true","false"]` → тумблер, другой список → выбор, отсутствие →
текстовое поле. Метаданные: `name`, `description`, `author`, `homepage`,
`manual`, `icon`, `open_url`.

**Модуль ≠ виджет.** Модуль — доставка и настройка конфигурации; виджет —
элемент на экране iOS. Модуль **может содержать** виджеты, обратное невозможно.

## 3.11 Rewrite, MITM, захват, URL-схема

- `url_rewrites` — три режима: redirect (3xx), header (прозрачная подмена URI
  и Host), reject.
- `header_rewrites` — add / replace / delete для request или response.
- `body_rewrites` — regex-замена и **jq-фильтры**.
- `map_locals` — подмена ответа локальным (status_code, headers, body).
- `mitm` — свой CA (`ca_p12`, `ca_passphrase`), `hostnames.includes/excludes`.
- `http_captures` — список хостов для записи обмена (с исключениями).
  **Это не механизм обнаружения отказов**, а запись заранее названных хостов;
  для HTTPS требует MITM.
- URL-схема: `egern:/start`, `/stop`, `/profiles/new?name=&url=`,
  `/proxies/new`, `/policy_groups/new?...`, `/subscriptions/new?url=`,
  **`/rules/new?type=&match=&policy=`**, `/modules/new?name=&url=`,
  `/connections`, `/connections/<id>`. Все поддерживают `x-success`.

# 4. ОГРАНИЧЕНИЯ EGERN (ЧТО НЕЛЬЗЯ)

Проверено по всем разделам документации:

1. **Нет доступа к состоянию конфигурации из скрипта.** Нельзя прочитать список
   групп, текущий выбор в группе, результаты замеров задержки. Аналога
   `$config.getConfig()` не существует.
2. **Нет API смены выбора политики.** Ни в `ctx`, ни в URL-схеме. Скрипт не
   может «переключить группу». Исключение: `http_request`-скрипт может
   подменить политику **для конкретного запроса** (2.18).
3. **Нет доступа к списку соединений.** Данные хранятся на устройстве (видны на
   странице «Хранилище» как логи и записи трафика) и показываются в Analytics,
   но программно не читаются: файлового API в `ctx` нет, `ctx.storage` — своё
   пространство. URL-схема умеет только **открыть** экран (`egern:/connections`).
   Есть ли ручной экспорт записей трафика — **НЕ ПОДТВЕРЖДЕНО**, проверить на
   устройстве.
4. **Отказавшееся соединение скрипту не видно.** `http_request` вызывается на
   запросе; для HTTPS требуется MITM. Пассивный сбор «что не загрузилось»
   невозможен — только активная проверка по списку.
5. **Параметры smart не настраиваются** (число выборок, пороги гистерезиса,
   вес джиттера, частота проб). Только `priorities`.
6. **Внешнего управляющего API нет** → zashboard и подобные панели не
   подключаются (они работают поверх Clash RESTful API). Подтвердить обратное
   не могу.
7. **Модуль не может содержать `proxies` и `policy_groups`** — узлы и группы
   только в главном профиле.
8. Минимальные интервалы (2.18): тест группы ≥60 с, обновление ресурсов ≥10 мин.
9. Максимальная глубина вложенности групп — **НЕ ПОДТВЕРЖДЕНО**.

| `routehub-netwatch.js` | флип -W/-C по сети | `conditional`-группа / правила `ssid`,`cellular` |
| Ручной чекер доменов | Loon не логирует незагрузки | активная проверка скриптом + список соединений глазами |
| `RouteHub-FailLog.plugin` + `[MITM] wikipedia` | отлов домена | `http_captures` точечно, включается на время |
| Дублирование узлов ×2 (-W/-C, 126 строк) | один порядок на всю подписку | две группы с разными `priorities` над **одной** подпиской |
| Каскад `fallback` из 6 региональных фильтров | нельзя ранжировать | веса `priorities` внутри `smart` |
| Разметка балла/скорости/☎ в именах узлов | негде хранить | коэффициенты и отдельные группы; имя = флаг + название |
| Риск порчи конфига при коммите (вывод №14) | нет отката | **история профиля**: снимок перед каждой правкой, восстановление в одно касание |

# 6. ПРОЕКТ АРХИТЕКТУРЫ ROUTEHUB НА EGERN

## 6.1 Классы маршрутизации A/B/C

**Разобранная и отвергнутая схема.** Сначала предполагалось: класс «РФ не в
whitelist» с пробником по конкретному домену (whoosh.bike). Схема **отвергнута**
возражением Дианы: если домен внесут в whitelist, пробник начнёт отвечать,
группа останется на DIRECT, а остальные домены класса перестанут работать —
молча. Ставка на статус одного домена недопустима.

**Принятая схема.** Признак whitelist — не «сайт лёг», а состояние сети:
зарубежное недоступно, российское доступно. Пробник — **зарубежная точка**,
статус которой под whitelist определён однозначно.

| Класс | Состав | Политика |
|---|---|---|
| **A** | анти-VPN домены (forg-lib whitelist-domains, hxehex+Сбер, банки ЦБ) — те, где VPN **вреден** | жёсткий `DIRECT` |
| **B** | всё остальное РФ (tbank, whoosh, мелкие банки, Apple) | `fallback [RH-Проба-Обычная, RH-Обход]` — норма обычный узел, whitelist → обход |
| **C** | зарубежное | `fallback [RH-АВТО, RH-Обход]` |

DIRECT из класса B **убран намеренно**: пока обычный VPN жив, РФ-домен
прекрасно работает через него, и вопрос «в whitelist домен или нет» перестаёт
что-либо значить.

Персональный список нужен только для перевода домена **из A в B** — то есть
ровно то, что сейчас делается вручную с whoosh.

Остаточный риск: домен из A ломается не из-за whitelist, а из-за собственного
анти-VPN — обход не поможет, правильный ответ DIRECT. Ловится вручную, случаев
единицы.

## 6.2 Скелет групп

```yaml
policy_groups:
  # --- обычный трафик, две сети над ОДНОЙ подпиской ---
  - smart:
      name: RH-АВТО-W
      urls: ["<Worker>/nodes?key=kN"]
      filter: "^(?!.*🙏)"            # обходные исключены из smart
      priorities: { ... }             # веса от Worker
      hidden: true
  - smart:
      name: RH-АВТО-C
      urls: ["<Worker>/nodes?key=kN"]
      filter: "^(?!.*🙏)"
      priorities: { ... }
      hidden: true
  - conditional:
      name: RH-АВТО
      rules:
        - ssid: { match: "<домашний SSID>*", policy: RH-АВТО-W }
        - cellular: { match: "*", policy: RH-АВТО-C }
      default_policy: RH-АВТО-W

  # --- обход: НИКОГДА не внутри smart ---
  - auto_test:
      name: RH-Обход
      urls: ["<Worker>/nodes?key=kN"]
      filter: "🙏"
      interval: 3600                  # раз в час, трафик платный
      latency_test_url: "http://cp.cloudflare.com/generate_204"

  # --- пробник состояния сети ---
  - fallback:
      name: RH-Проба-Обычная
      policies: [RH-АВТО]
      latency_test_url: "http://cp.cloudflare.com/generate_204"
      interval: 120
      timeout: 3

  # --- классы ---
  - fallback:
      name: RH-RU                     # класс B
      policies: [RH-Проба-Обычная, RH-Обход]
      latency_test_url: "http://cp.cloudflare.com/generate_204"
      interval: 120
  - fallback:
      name: RH-Главный                # класс C / FINAL
      policies: [RH-АВТО, RH-Обход]
      interval: 120

  # --- ИИ: sticky на каждый сервис ---
  - smart:
      name: RH-AI-Пул
      urls: ["<Worker>/nodes?key=kN"]
      filter: "^(?!.*🙏)"
      priorities: { ... }             # только годные узлы, веса от Worker
      hidden: true
  - fallback:
      name: RH-AI-Claude
      policies: [<закреплённый узел>, RH-AI-Пул, RH-Обход]
      latency_test_url: "https://claude.ai/"
      interval: 120
  # аналогично RH-AI-ChatGPT / -Gemini / -Grok / -Perplexity
  # Gemini и общий Google — на ОДНОМ узле (общие точки googleapis.com)

  # --- звонки ---
  - smart:
      name: RH-Звонки
      urls: ["<Worker>/nodes?key=kN"]
      filter: "^(?!.*🙏)"
      priorities: { ... }             # свои веса: важны jitter/потери, не скорость
```

Правила звонков переносятся один в один: `protocol: stun` и
`and: [{protocol: udp}, {dest_port: "3478-3481"}]` → `RH-Звонки`.
Важно: до 2.20 логическое правило с неподдерживаемым подправилом ловило **весь**
трафик — на более старых версиях такую конструкцию не использовать.

## 6.3 Роль Worker и `priorities`

Worker больше **не сортирует подписку**. Он:
- отдаёт узлы (формат Loon уже принимается — проверено на устройстве);
- генерирует профиль YAML с блоком `priorities` для каждой группы;
- держит реестр устройств, токены, персональные модули, историю.

Следствие: снят наш вывод №13 («порядок узлов один на все фильтры») — у
трафика, звонков и ИИ теперь **разные приоритеты при одной подписке**.

Требование к генерации: имена узлов в regex экранировать (`^...$`, эмодзи,
скобки `[VPN]`).

## 6.4 Сети

Дублирование узлов не нужно (см. 6.2): `conditional` выбирает между двумя
smart-группами по SSID / типу сотовой. Подписка отдаётся один раз — 72 строки
вместо 126.

## 6.5 ИИ

**Отбор — только по измерению, географических исключений НЕТ.**
Отсечение СНГ отменено: у провайдера на узлах СНГ может стоять своя внешняя
маршрутизация, и ИИ через них работает. Страна остаётся **тайбрейкером** (при
сопоставимых результатах предпочитается узел той же страны — смена страны для
Claude дороже смены узла).

Что меряет скрипт по каждому узлу:
- фактическую страну выхода через `cdn-cgi/trace` (не из имени);
- достижимость публичной точки каждого сервиса: код ответа + признаки
  страницы-заглушки (200 с проверкой Cloudflare ≠ «работает»);
- задержку/потери попутно.

Расхождение «имя говорит Казахстан, выход даёт NL» — полезный сигнал: это и
есть узел с внешней маршрутизацией.

Что решает Worker: отсев негодных, EWMA по истории (разовый сбой не роняет),
учёт скорости и устройства (назначения **персональные**: у k1 и k2 разные
операторы), выбор узла на сервис, запись его в `priorities: 0` или первым
членом `fallback`.

**Дисциплина смены** (иначе автоматика начнёт дёргать IP):
- смена только после 3 проваленных циклов подряд;
- кандидат должен выигрывать с запасом;
- cooldown — сутки на сервис;
- при прочих равных — узел той же страны;
- каждая смена → `ctx.notify` (сервис, старый узел, новый).

**Вердикт Дианы как обратная связь.** Пробник не видит ограничений, наступающих
после входа в аккаунт, и не предсказывает бан. Поэтому в виджете/панели по
каждому сервису две кнопки: «работает» / «не работает». Вердикт уходит в Worker
и хранится как факт по паре «узел + сервис» со сроком годности: «не работает»
исключает узел из кандидатов, «работает» повышает вес. Вручную назначать ничего
не нужно — автоматика отбирает, вердикт корректирует.

**Аварийная ступень — только вручную.** Разблокирующий DNS (Comss.one и
подобные) в автоматике не участвует: отдельный модуль, `env_schema` с тумблером,
по умолчанию выключен.

## 6.6 Как работают разблокирующие DNS (зафиксировано, чтобы не путаться)

ИИ-сервисы смотрят на **IP клиента**, не на DNS. DNS решает, к какому адресу
пойдёт трафик. Сервисы вроде Comss.one отдают на выбранные домены адрес
**своего прокси**, который перенаправляет запрос дальше — то есть это маленький
VPN, выбираемый через DNS-ответ. «Отваливается» = перегружен или заблокирован
их релей.

Последствие: трафик идёт через чужой сервер с общим для всех пользователей
адресом. Для Claude это прямо противоречит принципу sticky (защита аккаунта),
поэтому — только аварийно и вручную.

## 6.7 Режим РКН (whitelist)

Переключение режимов **не требуется**: `fallback` реагирует сам (пробник
класса B/C падает → уходит на обход; восстановился → вернулся). Это и сейчас так
работает на Loon — обход внизу каскада, скрипт им не управляет.

`routehub-rkn.js` сохраняется только ради истории смен и уведомления.
Управлять группами он всё равно не смог бы (см. 4.2).

Оговорка прежняя: под whitelist Worker доступен только через обход, профиль в
этот момент не обновится — и не требуется.

## 6.8 DNS — каркас

```yaml
dns:
  bootstrap: [system, 1.1.1.1]
  upstreams:
    secure:  ["h3://dns.cloudflare.com/dns-query", "https://8.8.8.8/dns-query"]
    ru:      ["https://77.88.8.8/dns-query"]
    unblock: ["https://dns.comss.one/dns-query"]   # только по тумблеру модуля
  forward:
    - proxy_rule_set: { match: "<список РФ-доменов>", value: ru }
    - domain_regex:   { match: "^ad(s)?\\.", value: reject }
    - domain_wildcard:{ match: "*", value: secure }
  proxy_nameservers: ["https://1.1.1.1/dns-query"]
  block_ips: ["0.0.0.0", "127.0.0.1"]
  public_ip_lookup_url: "https://ifconfig.me/ip"
```

Этап J (TikTok) сводится к `hosts` + одному правилу `forward`.
Конкретные серверы — решение Дианы.

## 6.10 Спидтест — переработка

Условия «ночь, зарядка, заряд ≥50%» **отменены** (замер быстрый, расход батареи
незначительный). Новое:
- параллельные батчи — лимит ~6 соединений на хост снят в 2.20;
- `timeout` до 600 с вместо 200;
- `ctx.http` с `policy: <узел>` вместо `node:`;
- **обходные узлы не трогать никогда** (трафик платный);
- результат — не в имена узлов и не в метки, а в коэффициенты `priorities`
  через Worker;
- окно и интервал — через `env` модуля (тумблеры в UI).

Ранжирование обходных узлов — **не** через smart (частота проб не настраивается,
а под whitelist обход остаётся единственным живым и пробы участятся), а через
`auto_test` с `interval: 3600` и лёгким пробником 204.

## 6.11 Виджет

**Малый:** режим (норма / whitelist) цветным маркером; флаг страны
закреплённого узла Claude; время последней связи с Worker.

**Средний:** + закреплённые узлы по сервисам ИИ; сеть (SSID или тип соты из
`ctx.device`); сколько узлов живо по последнему замеру.

**Большой:** + таблица топ-8 узлов (имя, Мбит/с, задержка, джиттер); возраст
данных; полоска истории смен режима за сутки; расход обходного трафика, если
Lastdep отдаёт `Subscription-Userinfo`.

**Локскрин (accessory):** режим + страна узла Claude.

**Действия по нажатию** (URL-схема, не скрипт): `egern:/connections`,
`egern:/rules/new?type=domain_suffix&match=<домен>&policy=RH-RU`,
`egern:/start`, `egern:/stop`, `egern:/profiles/new?url=…`, ссылка на панель
Worker. Кнопки «работает/не работает» по сервисам ИИ — через `ctx.http` на
Worker при обновлении виджета либо через панель.

**Чего в виджет положить нельзя:** текущий выбор в группе, задержки, которые
меряет сам Egern, счётчики трафика приложения — это состояние приложения.

## 6.12 Модули и персонализация

```yaml
modules:
  - url: "<Worker>/t/<token>/module/direct?key=kN"  # класс A
    update_interval: 300
  - url: "<Worker>/t/<token>/module/ru?key=kN"      # класс B (личный список)
    update_interval: 300
  - url: "<Worker>/t/<token>/module/dns?key=kN"     # тумблер разблок. DNS

  - url: "<Worker>/t/<token>/module/scripts?key=kN" # скрипты + env_schema
```

Добавление домена = запись в D1 + обновление модуля через 5 минут, **без
перегенерации всего профиля**. Мгновенный ручной путь — `egern:/rules/new?…`.

Списки **раздельные по классам и персональные по устройству** (`k1`/`k2`) —
разные операторы и регионы.

## 6.13 Worker v2 — изоляция

| Что | Как |

# 9. ОТКРЫТЫЕ ВОПРОСЫ И РЕШЕНИЯ ДИАНЫ

1. Конкретные DNS-серверы (`secure`, `ru`) — выбрать.
2. Домашние SSID для `conditional` — уточнить (нужны и для k1, и для k2).
3. Готовность пускать отдельные ИИ через сторонний разблокирующий DNS — с
   учётом риска для аккаунтов (сейчас: только аварийно, вручную).
4. Формат имён узлов после миграции: оставить ли ⭐/🚀/🙏 или только флаг + название.
5. Иконки групп: SF Symbols или свои картинки (URL). Свои держать **на Worker**,
   не в репозитории — под whitelist GitHub недоступен.

# 10. РИСКИ

1. **Пробы могут тратить платный обходной трафик.** Обходные узлы держать вне
   `smart`, только `auto_test` с `interval: 3600`. Заложено в 6.2/6.10.
2. **smart под whitelist** — все члены проседают одинаково, взаимный порядок
   сохраняется; обход не является членом smart, поэтому «выучить, что обход
   хорош» невозможно.
3. **Объём работ** — примерно этапы C и D заново плюс половина Worker.
4. **Молодой продукт**: 2.16 → 2.20 за пять месяцев, в каждом релизе правки
   логики групп и failover. Критерий G.3 («неделя без вмешательства») проверять
   заново.
5. **Нет самодиагностики из скрипта** — часть состояния смотрится глазами.
6. **Логические правила** на версиях до 2.20 при неподдерживаемом подправиле
   ловили весь трафик.
7. **Два клиента одновременно** — активен всегда только один VPN-профиль;
   Egern ставится рядом с Loon и живой конфигурации не мешает.

# 12. ЖУРНАЛ РЕШЕНИЙ ЭТАПА K

| Решение | Почему |
|---|---|
| Текущий RouteHub на Loon сохраняется целиком | ничего не ломать; переход только после доказанной работоспособности |
| Worker v2 — ветка `egern`, отдельная D1 | общая база перепривяжет `nonce` устройств (вывод №12) |
| Географические исключения (СНГ) отменены | появляется измерение; у провайдера на СНГ-узлах бывает своя внешняя маршрутизация |
| Страна — только тайбрейкер | смена страны для Claude дороже смены узла |
| Класс B без DIRECT, пробник — зарубежная точка | ставка на статус одного домена рушится, когда домен вносят в whitelist |
| Обходные узлы вне `smart` | иначе платный трафик на пробы и «обучение» на обходе |
| Обход ранжируется `auto_test`, интервал 3600 | у `smart` частота проб не настраивается |
| Условия спидтеста (ночь/зарядка/заряд) сняты | замер быстрый, расход батареи незначительный |
| Разблокирующий DNS — только ручной тумблер | чужой релей с общим IP противоречит sticky для ИИ |
| Узлы для ИИ назначает Worker, Диана даёт вердикт | пробник не видит ограничений после входа в аккаунт |
| Дублирование узлов -W/-C отменено | `conditional` + две smart-группы над одной подпиской |
| Разметка балла/скорости в именах узлов отменена | данные уходят в `priorities` |
| `routehub-rkn.js` сохраняется только для истории | переключением всё равно управляет `fallback` |
| Дашборд `rh.box` не переносится | Analytics приложения перекрывает его функции |
| zashboard не подключается | требует Clash RESTful API, которого у Egern нет |
| Ручное создание сущностей в UI Egern запрещено | профиль генерирует Worker; иначе расхождение |
